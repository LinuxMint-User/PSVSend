# PSV 自制游戏开发建议

> 2026-10-31 整理。偏工程实践，面向「用 VitaSDK 从零做一个小到中型游戏」。
> 平台底层经验（app0 读盘、字体、线程、日志、真机验证）见
> [psv-app-dev-lessons.md](psv-app-dev-lessons.md)，本文不重复。

## 1. 技术栈：先定 2D / 3D，再定框架

- **2D**：直接用 `vita2d`。它够用、省心，瓶颈在绘制调用数——把精灵打进图集、按纹理合批即可。
- **3D**：两条路——`vitaGL`（OpenGL ES 封装，上手快，抽象层有成本）或原生 `SceGxm`
  （性能上限高、坑多、着色器要离线编译）。先用 vitaGL 做原型，确认玩法后再决定要不要下沉。
- **不要一上来写引擎**。PSV 上大部分"做不下去"的项目，都是先堆引擎和内容，最后发现帧预算、
  内存根本不够。
- Gxm 的上下文是**单线程**的：只在主线程提交绘制，别在音频 / 资源线程里碰 GPU。

## 2. 帧预算按 16.7ms 倒推

444MHz 的 Cortex-A9 做逻辑并不宽裕。经验分配：

- 逻辑 + 动画：≤ 5ms；
- 渲染提交：≤ 5ms；
- 余下留给音频、IO 抖动和系统开销。

做一版帧耗时 HUD（逻辑 / 提交 / 等待 vsync 分开计时），比事后猜快得多。掉帧时先看是 CPU
（逻辑/提交）还是 GPU（填充率/绘制调用）——两者优化方向完全不同。

## 3. 渲染：顺着 PowerVR 的 TBDR 脾气

- 大量小 draw call 比想象中贵：**合批、图集、顶点色**，少切纹理、少切着色器。
- 少做 render-to-texture 和多 pass：切换渲染目标有 resolve 成本，TBDR 最怕来回切。
- **填充率有限**：全屏半透明、渐变叠层、大粒子是最常见的掉帧源。3D 掉帧时先降内部分辨率
  再考虑砍效果；阴影/后处理要用最土的做法（预烘焙、单 pass、低分辨率缓冲）。
- 纹理、着色器、管线**在加载期建好**，别在第一次绘制时才创建（会卡一帧甚至几帧）。
- 用 `sceDisplayWaitVblankStart` 做帧同步，别用 sleep 凑时间。

## 4. 资源：app0 是压缩流，打包顺序读

- 游戏资源**打成一个包 + 偏移表**，加载时顺序读进 RAM；不要几百个小文件各开一次——
  `app0:` 是 deflate 压缩流，随机读一块就要解压，代价极高（本项目字体实测 ~40ms/字形）。
- 加载画面期间做所有读盘、解码、纹理上传；**帧循环里绝不做同步 IO**。
- 纹理避免每帧上传。动态内容（视频、相机）才考虑流式，其余常驻。
- 音频尽量离线解码成 PCM 再打包，或在加载线程里解码，别在主线程里解 OGG。

## 5. 字体与 UI 用预渲染

- HUD 用位图字体或图集，别在运行时排版 TTF。Vita 上 TTF 光栅化的成本不可控，且 libvita2d
  的字形 atlas 有"固定 512×512、溢出静默不画"的隐藏行为（见应用篇 §3）。
- 多语言就按语言各打一套字形图集；菜单文字量小，图集完全够。
- UI 也要考虑手柄操作，别只做触摸。

## 6. 内存：UMA，但必须有池

- CPU/GPU 共用物理内存；GPU 可见的缓冲用 `sceKernelAllocMemBlock` + `sceGxmMapMemory` 分配。
- **帧循环里零 `malloc`**：对象池 + 预分配，实体、粒子、音效通道都走池。
- 贴图、关卡、音频常驻还是换入换出，要提前定量；"内存不够再优化"在掌机上通常是重写。

## 7. 线程分工

- 主线程：逻辑 + 提交绘制（Gxm 只能在这里）。
- 音频线程：SceAudio 是**拉模式**，`sceAudioOutOutput` 会阻塞到缓冲被消费；用独立线程 +
  双/三缓冲喂数据，绝不在渲染线程里等它。
- 加载/解码线程：资源、音频解码、网络都放这里，只把完成事件投给主线程。
- 四核不要浪费，但也别为了并行而并行：小任务拆线程的同步成本可能比收益高。

## 8. 手感：固定时间步 + 渲染插值

- 逻辑固定 60Hz 步进，渲染做插值；帧率波动时游戏速度不飘。
- 输入每帧 `sceCtrlPeekBufferPositive` 取一次，逻辑里不要反复查询；摇杆记得做死区。
- 触摸（前/后）和体感是加分项，不要作为唯一输入路径。

## 9. 存档：原子写

- 先写 `.tmp`，`fsync`/关闭后再 `rename` 覆盖正式档；直接覆盖遇到断电/拔卡就是坏档。
- 存档格式带版本号，方便以后迁移；别把内存结构体直接 dump 进去。

## 10. 调试与验收

- **真机为准**。Vita3K 适合快速迭代逻辑，但性能数据和驱动行为不可信，别拿它测帧率。
- 用 `sceKernelGetSystemTimeWide` 打点，先定位再优化；日志文件 + 构建号（`dXXX`）是最省事的
  反馈方式。
- 每个里程碑都做一次真机冷启动验收：安装、首启、加载、退出、再进。

## 11. 别假设的平台能力

- 组播接收、后台下载/通知、系统 SSL、实时钟——这些在 Vita 上不可用或不可靠（本项目逐条踩过）。
- 联机发现、在线鉴权、每日计时这类设计，要提前准备离线/降级方案。
- 别假设玩家机器超频或装了插件；按默认时钟设计预算。

## 12. 先做最小闭环

清屏 + 一个精灵 + 输入 + 出声 + 稳定 60fps，先把这个跑通，再加内容。

建议的推进顺序：

1. 窗口 / 帧循环 / 输入 / 退出；
2. 一张图 + 一张图集 + 位图字体；
3. 音频线程 + 一个音效；
4. 一个完整关卡（加载 → 玩 → 结算 → 存档）；
5. 再做第二关、菜单、设置。

## 附：可参考的实测数字

以下来自 PSVSend 在真机（默认时钟）上的测量，可当作"这颗机器大概什么水平"的参照：

| 项目 | 数值 |
|---|---|
| 后摄采集 | 640×480 / 320×240 均 30fps |
| 单帧 QR 解码（纯 CPU） | 640×480 ≈147ms / 320×240 ≈112ms |
| 纹理上传 320×240 | ~1ms/帧 |
| TLS 收发吞吐 | 发送 4.66 / 接收 5.21 MiB/s |
| 字体从 app0 随机读 | ~40ms/字形（内存 face 0.19ms） |

结论：**CPU 单线程能力很有限，重计算一定要拆线程或降频次；GPU 侧则要敬畏填充率和绘制调用数。**
