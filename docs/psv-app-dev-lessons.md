# PSV 应用开发经验（PSVSend 沉淀）

> 2026-10-31 整理，2026-11-01 补扫码取景与界面手感两批。内容来自 PSVSend（PS Vita 上的 LocalSend v2 客户端）的真机调试记录，
> 面向「在 Vita 上做联网 / 工具类应用」的场景。游戏向的建议见
> [psv-game-dev-notes.md](psv-game-dev-notes.md)。
> 每条结论尽量附实测数字，细节可查 [design.md](design.md) 与 README 的功能条目。

## 1. 平台限制先查，别照搬 PC 假设

- **Vita 收不了 UDP 组播，也绑不了 53317 端口**。协议文档上写得通，不代表平台能做。
  发现机制只能反过来设计：主动扫 /24 子网 + 等对方 register。
- **`app0:` 是 deflate 压缩流**，随机读的代价极高（见 §2 字体）。凡是"频繁随机访问"的资源
  （字体、图标、音频片段）都应该启动时一次性读进 RAM，而不是用时再读。
- **系统 `SceSsl` 对 homebrew 不可用**，TLS 只能自带 mbedTLS；且 TLS 1.3 没有 per-cert 回调，
  证书指纹 pin 依赖 TLS 1.2。
- **没有实时钟**。检查更新的周期判定、证书有效期之类的时间逻辑，要么用远端响应 `Date` 授时，
  要么别依赖墙钟。
- **不能后台下载、没有通知中心**。手机/PC 上"理所当然"的常驻能力，在 Vita 上直接判死，
  方案要提前想退路，别做到一半才发现。

## 2. 性能：瓶颈几乎从不在你以为的地方

- **先分清"算得慢"还是"读得慢"**。字体卡顿的真因不是渲染，而是 libvita2d 默认用文件 face：
  FreeType 每取一个新字形都要在 `app0:` 里随机读一块再解压，实测 **~40ms/字形**；同样字体改成
  内存 face 是 **0.19ms/字形**，差 150~180×，且与字号无关（砍字号档位无效）。
  改成启动时读进 RAM + `vita2d_load_font_mem` 后，开屏预热 5315ms → **65ms**。
- **按 CPU 特性选算法**。Cortex-A9 没有 AES/SHA 硬件指令，实测 ChaCha20-Poly1305 比 AES-GCM
  快约 20%。"主流默认"不一定适合这颗 444MHz 的 CPU。
- **关键路径上别做小事**。TLS 握手从 447~521ms 降到 **230~250ms**，靠的不是换算法，而是把设备
  身份解析挪到启动、握手内不打日志——`dlog` 是同步写 ux0，一次几十毫秒，足以毁掉对方的 500ms
  发现预算。
- **吞吐靠流水线重叠，不靠单点优化**。收体三级流水（解密 / sha256 / 写盘各一条线程，3×64KB
  轮转）使接收 **2.81 → 5.21MiB/s**；发送读/发双缓冲 **3.53 → 4.66MiB/s**。两端随后都压在
  裸 TCP 标定上限上——到这一步就是真上限，再调线程数没意义。
- **profile 永远比直觉准**。摄像头基准里"320×240 应该快 4 倍"的常识是错的：PC 上 profile 显示
  75% 耗时在 quirc 的 `perspective_map` / `fitness_cell` / `fitness_all`（网格拟合），与像素数
  几乎无关，实测只快约 24%。
- 方法论：**读 / 算 / 等 分段计时**。等待也占墙钟，不拆开就永远不知道时间花在哪。

## 3. 把第三方库当成"有隐藏行为的依赖"

libvita2d 的几个坑，全部是"沉默失败"型：

- 字形 atlas 是**固定 512×512 单页、永不淘汰**，装不下时上层直接跳过绘制，**不报错、不崩溃**，
  只表现为某些字/图标凭空消失。
- 字形缓存**不分字号**：同一字形先小字号缓存、再大字号绘制时整块放大，出现笔画不均、横向条纹。
  正解是**按像素字号分槽**，每个槽一个字体对象（各自 atlas、`draw_scale` 恒为 1）。
- UTF-8 解码只认 2/3 字节，**不认 4 字节码位**，图标字体里超出 U+FFFF 的字形画不出来。

结论：不跟它较劲。图标改成**构建期预渲染图集**（按固定顺序、1:1 绘制、POINT 采样），
字体按字号分槽，绕开全部隐性行为。

## 4. 并发与内存

- **线程不要强杀**。收尾时等不到线程退出就遗弃整条流水线（不 DeleteThread、不 free 缓冲、
  不删临时文件），转 ZOMBIE 槽位，线程真退出后由 reaper 回收。谁抢先释放谁就制造 UAF——
  本项目的 P1-4 就是这么来的：写盘阻塞超过 10s，线程访问了已释放的上下文。
- **UMA 架构**：CPU/GPU 共用物理内存，字体读进 RAM 不会额外吃显存。但要有数：设置页内三份
  CJK 同驻的峰值约 **49.9MB**，真机能扛，不代表可以随便常驻。
- **后台线程只投事件**，主线程每帧消费。网络、解码、校验都不该在渲染线程里做事。

## 5. UI 的"可发现性"比功能本身更容易翻车

- 960×544 + 手柄，**主路径必须是按键**；触摸是"防死锁 + 顺手"，不追求全操作对等。
- 设置页值行从"点左右半屏 / 确认键循环"改成**右侧滑出选项面板**，原因很单纯：前两种不看代码
  根本发现不了。面板内 ↑↓ 选档、确认应用且不收起、✗ 取消——交互统一比省一次按键重要。
- 行几何（行高 / 步进 / 内边距 / 字号）和长文本省略口径收成**一份公共常量**，否则每个页面都会
  各写一套，最后没法统一调整。
- **图标自解释不了时，给"按住某个键变文字"**。页头三个扁平图标平时只画图标，按住 R 时从右往左
  逐个变宽换成文字（宽度按当前语言实测、右端锚定），既不长期占位，又能让用户按一次就学会功能。
- **没有视觉入口的操作靠空闲 tips 教**。主页细条在无选中项 / 非扫描时轮播 5 条操作提示
  （按住 R、长按 △ 清空、网页共享地址…），8 秒一条；一有内容就立即让位，不抢信息位。
- **滚动惯性要能立刻停**。所有列表共用一套抬手速度模型（150 px/s 启动、2600 px/s 上限、140ms
  衰减），碰边硬停、不做回弹；点按 / 按键 / 开选项面板 / 离开页面都立即停。惯性是输入层给出的
  速度量，页面只按真实 dt 积分，不自己猜方向。
- **纯展示模块不要塞页面语义**。页脚 R 段最终定为"页面声明优先、模块仅在确有段被丢弃时兜底补"：
  无条件补会让没用到 R 的页面出现死提示，只按溢出补又会让文案短的语言永远看不到。

## 6. 工程方法

- **实测 > 估算**。性能问题一律先做基准、看日志，不靠猜。本次为扫码功能专门做了"实验室 ›
  摄像头基准"，一次开始跑完三档并写 `log.txt`，结论直接进文档。
- **实验性功能挂在正式版的"实验室"里手动触发**。不用造触发文件、不用单独出测试包，测完还能
  长期留着。
- **构建号（`dXXX`）进日志和"关于"页**：反馈时只看一眼就能确认刷入的是不是目标固件。
- **一版只做一件事**；改动先给 diff 再提交，未批准不动分支/推送。
- 网络类功能配**伪对端脚本**（如 `scripts/fake-send.py`），能稳定构造"单文件校验失败""中途断流"
  之类真机难以复现的场景。

| 项目 | 数值 | 结论 |
|---|---|---|
| 字体文件 face / 内存 face | 43.5ms / 0.19ms 每字形 | 资源必须进 RAM |
| 开屏字体预热 | 5315ms → 65ms | 内存 face + 常驻 |
| TLS 握手 | 447~521ms → 230~250ms | 关键路径挪走同步写盘 |
| 发送吞吐 | 3.53 → 4.66 MiB/s | 读/发双缓冲流水 |
| 接收吞吐 | 2.81 → 5.21 MiB/s | 解密/校验/写盘三级流水 |
| 页内三份 CJK 峰值 | ~49.9MB | UMA 下可接受 |
| 后摄采集 | 30fps（640×480 / 320×240） | 采集不是瓶颈 |
| QR 解码（quirc） | 640×480 ≈147ms / 320×240 ≈112ms | 瓶颈在网格拟合 |

| 扫码吞吐 | 6~9fps | 连续扫 2~3 帧确认即可 |
