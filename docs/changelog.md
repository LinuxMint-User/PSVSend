## 功能与实现记录

- [x] VitaSDK 交叉编译环境 + vita2d 渲染骨架 + VPK 打包（含 LiveArea 素材）
- [x] LocalSend v2 发送链路：UDP 组播发现 / register / prepare-upload / upload
- [x] 文件发送（PSV → 手机 / PC，HTTP 明文与 HTTPS 加密均支持）
- [x] TLS 加密传输（mbedTLS 3.6.5，含 mTLS 客户端身份）：发送方向按对端 protocol 走 HTTPS；**接收方向同一端口同时服务 HTTPS 与明文 HTTP**（首字节 `0x16` 判 TLS，d173~d177）
- [x] 设备身份验证（d195~d200）：与官方 VerifyPage 同口径——两侧各自把「本机证书指纹」与「对端证书指纹」按字典序排序后**直接拼接成 128 hex**（不哈希、不截断），屏幕上应一致。入口是**发送等待页**与**接收确认页**的「验证」按钮，方向键切焦点、也可触摸；**只在加密连接出现**（明文对端没有证书指纹可比，官方同样把该按钮置灰）。页面**同屏给出两种表示**：左半 16 个图标（对 128 hex 再 SHA-256、取前 16 字节做 base-260 取图集格子，与官方图标模式完全同口径），右半 8 行 × 16 字符的原始文本码——任一半对上即可。官方是二选一（默认图标、可切 Text），PSV 省掉切换、两种并排
- [x] 文件接收（手机 / PC → PSV）：prepare-upload 弹确认 → upload 流式写盘，兼容无 Content-Length 的 chunked 上传
- [x] 主动扫描：Vita 收不了 UDP 组播，改向局域网 /24 各 IP 主动 HTTP 探测补全设备表
- [x] 网络稳定性：待机唤醒 / Wi-Fi 断开恢复后自动恢复发现（watch 看门狗 + 低频 netctl 轮询，v2.0.0）；断网「活性刺激」改非阻塞发包，Wi-Fi 重连过渡态不再卡住界面与按键（d65）
- [x] 渲染稳定性：修复偶发 GPU render crash（界面撕裂后崩溃）——每帧等待 GPU 渲染完成（v2.0.0）
- [x] 多语言界面（设置页语言行可切换，语言清单见下条）与设置页「关于」行（版本 + 构建号 + 适配 LocalSend 说明；d234 起从底部移到顶部并精简为单行）
- [x] 字体性能（d120-d126）：定位到"切页 / 滚动首见某字就卡顿"的真因——libvita2d 默认开的是**文件 face**，而字体放在 VPK 的 `app0:`（deflate 压缩流）里，FreeType 每取一个**新**字形轮廓都要包内随机读一块再解压，实测 **~40ms/字形**（同字同号对照：文件 face 43.5ms vs 内存 face 0.19ms，差 150~180×，且与字号无关）。改为启动时把字体文件一次性读进 RAM、字体对象走 `vita2d_load_font_mem`——开屏预热总耗时 5315ms → **65ms**，开机到主界面 ≈665ms；此后**删掉开屏画面与全部字形预热逻辑**（不再需要）。字体换 **Noto Sans**（SIL OFL 1.1，随仓库入库）：拉丁一份 + CJK 简 / 繁 / 日三份地区版本，按界面语言选字形
- [x] 检查更新（v2.1.0）：设置页可手动检查，也可自动定期检查（默认每周，可每天 / 每月 / 关闭）。后台线程先拉 Gitee 镜像仓库的 `src/core/config.h` 版本宏（主源），失败再试 GitHub Releases atom 兜底，与本地版本宏比对。**不新增任何版本文件**：config.h 是唯一版本真源（发版必改、镜像同步自然带上）。自动周期用远端响应 Date 授时判定，PSV 无实时钟也不误判
- [x] 保存目录可选（v2.1.0 后）：设置页“存储 → 保存目录”可改**默认接收目录**（config `saveDir` 持久化）；接收 Setup 可临时改**本次**目录（仅当次会话，新请求回默认）。目录选择器复用文件浏览的 ux0 目录树（仅列文件夹，选定 = 当前所在目录）
- [x] 界面交互（d86-d100）：主页改为**两栏**（设备栏 + 已选文件栏，左右位置可换，设置项「布局」）；发送等待独立成页（等对方接受，接受后自动进传输页，被拒 / 连不上就地报错）；页脚提示条口径统一（确认键提示跟随当前焦点动作、两键同一动作合并成一段、固定提示靠左而可变提示靠右）；十字键提示改为**方向可用性指示**（列表到顶 / 到底时对应方向变灰，提示按了没用）；扫描中提示初为 “...N of M possible hosts, K found, you could proceed”（d99/d100，避免把 `N/M` 读成进度门槛），后于 d165 简化为「扫描中… N/M」并移到设备栏标题行右侧（见本区末条）
- [x] 主题系统（d102 / d106-d109）：色系（Yaru / OLED / 自定义）× 明暗（深色 / 浅色）两个正交轴，设置页「主题」「外观」两行切换（OLED 固定深色）；**自定义主题**不写死色值，只存主色 HSV（config `customH/customS/customV`）运行时推导整套配色，设置页「主色」行（**仅自定义主题下显示**）进色盘页——上下选条、左右调值、实时预览整套配色，确认落盘、取消还原；页脚按键提示条独立成 `hintbar` 模块（键位图标 / 段排序 / 排版统一由模块处理，加新按键只改该模块）
- [x] 多语言扩展（d111-d113）：语言行扩到 5 项——跟随系统 / English / 简体中文 / 繁中（台灣）/ 繁中（香港）；两版繁中**按地区用词习惯分别翻译**（網路 / 網絡、資料夾 / 文件夾、每週…，不是繁简一对一转写）。修复「跟随系统」此前恒回退英文（`sceAppUtilSystemParamGetInt` 需先 `sceAppUtilInit`，应用从未初始化）；系统只区分简繁、推不出台港，而 PSV 的中文（繁體）本地化基底是台灣用語，故系统繁体默认台灣，港式用词在语言行手选
- [x] 日语界面（d126）：语言行再加 **日本語**（共 6 项）。译文表加日语一列，按日语习惯**意译**而非汉字直搬（如 Devices → デバイス、Up → 上へ）；CJK 字体按界面语言取地区版本（简 `sc` / 繁 `tc` / 日 `jp`），换语言时帧外重建字体对象（首次切到某地区读盘 ~1.6s、之后常驻 RAM；**d148 起设置页内已后台预读，切语言不再等这 1.6s**）
- [x] 发送侧并发上传（d144）：多文件发送不再逐文件串行——prepare 后起 N 个 worker（N = 设置页「并发上传数」，默认 3、范围 1-6，1 = 退回逐个发）**共享取号**，每个文件一条独立连接并发上传。**每文件独立成败**（HTTP 4xx/5xx、对端未回 token、读文件失败只标该文件，其余照传）；**连接级失败（连不上 / 握手失败 / 中途断流 / 等不到回执）判"对端不在"→ 立即全局中止**（实测断流后 212ms 整批收尾，不再让各路各自等满 6s/30s 超时），终态由监督者 join 完全部 worker 后统一判定。实测 6 并发传 66MB / 6 文件正常，未被对端限流（无 429）；注意**总吞吐受无线链路限制**，并发省下的是文件之间那一段段串行等待，故小文件多时提升明显、单个大文件为主时收益有限
- [x] 设置页改值交互（d145/d146）：所有**值行**（主题 / 外观 / 界面语言 / 确认键布局 / 布局 / 并发上传数 / 发送前校验 / 接收时校验 / 自动检查）改成**点整行（或焦点行按确认）→ 右侧滑出选项面板**——面板里 **↑↓** 选档、确认 = 应用并落盘（**面板不收起**，可以连着试几个档看效果）、**✗** 或点面板外 = 关且不应用；2 档也走面板（交互统一），「外观」在 OLED 主题下无档位、开不出面板（页脚确认段画灰）。动作行（主机名 / 保存目录 / 主色 / 检查更新）点了仍直接执行。原"确认键循环改值"与"点行左半减 / 右半加"（后者没有任何提示、不看代码发现不了）两套玩法一并废除
- [x] 进度页收尾表现（d147）：总进度条的**颜色跟随终态**——运行中 / 全部成功 = 主色，**部分失败**（完成但有文件挂）= 警示色，**取消 / 整体失败** = 危险色（原来恒为主色、跟传输中一模一样，所以部分失败停在半路时看着像"还在传"）。**填充不变**：仍按"已传 / 声明总大小"，拉满等于谎报字节数（也会和高级面板的 `Files x/y` 打架）。另外修掉高级面板的**速度**——原来用"总大小 × 百分比"反推已传字节，1% 粒度截断（传输开头恒显示 `0.00 MB/s`）、终态还会虚高，现改用真实已传字节；**d179 起速度读数改用 2 秒滑动窗口**（200ms 采样，结束后冻结终值），不再用"累计平均"（分母含 prepare / 对方确认 / PIN 键盘等待，读数会从 0 缓慢爬升）；**d194 起每次新传输都从 0 起算**，两笔间隔很短时不会再沿用上一笔的样本
- [x] 设置页字体预读（d148）：在设置页切界面语言，原先要现读 16.4MB 才有对应地区字形（主线程冻结 ~1.6s）。现在**进设置页即起后台线程预读另两份 CJK**（拉丁与当前语言那份本已常驻），页内切语言退化为从 RAM 建字体对象——真机十次连续切换（英 / 简 / 繁台 / 繁港 / 日 / 跟随系统）无卡顿；**出设置页停线程并释放非常驻副本**，页外常驻 ≈17MB 与从前一致。页内峰值 ≈49.9MB（三份 CJK 同驻），真机验证无内存不足
- [x] 界面绘制层收敛（d149-d157）：列表行的几何（行高 / 步进 / 左右内边距 / 行内字号）原先散在 5~6 个文件各取各值，现收成 `ui.h` 里**一份常量表**；行型收敛成**值行 / 两行排 / 密集行**三档，由 `row_geom()` 统一给出锚点与字号（右端值宽度不再靠写死 `r.w-200` 猜）。行内长文本按类别自动省略：**路径保尾部**（`…/PSPSEND/Download`，末级目录才是要看的）、**文件名保扩展名**（中间省略）、其余截尾。观感变化：列表整体下移 8px、行距略松、左内边距统一 24（接收设置页最明显）
- [x] 界面修复（d153 / d155）：主页两栏**长按拖动不再串栏**（拖设备栏 / 文件栏会错改另一栏的滚动）；接收确认页**文件较多时预览不再溢出卡片**；"文件名过长将自动缩短"**不再误报**（此前按"名字有没有变短"反推，剥掉对方送来的路径前缀后正常名字全被判成过长）
- [x] 版本标识与更新检查解析（d158）：`config.h` 新增 `PSVSEND_BUILD_TAG`（**构建魔数**，如 `d158`），boot 日志与设置页「关于」共用这一处来源——「关于」现在显示 **v2.2.0 (d158)**，装完看一眼即可核对刷入的是不是目标固件、不必翻日志；该宏只作标识，**不参与版本比较**。同批把更新检查的版本宏解析由"找宏名 + 取其后第一个引号串"收紧为严格认**定义行**（行首 `#define`、宏名是其后首个记号、值须数字开头，不满足继续找下一处），注释或其它宏里出现同名 token 不再可能被误当版本串
- [x] 主页交互完善（d159-d165）：**文件栏三角键「清空全部」改为长按蓄力触发**——原先它与设备栏的短按扫描同一个键、按一下就直接清空，容易被误当成扫描而误操作；现在按住 **△** 约 700ms，三角图标周围画进度环（灰底环 + 主色进度弧，12 点起顺时针），满格才清空，松手则进度渐进回落（回落中重新按住从当前进度续涨），清空后该段变灰。设备栏 **△** 短按扫描不变。实现上**长按判定放在输入层**（与方向键长按重复同属一套状态机，页面只消费动作、不判断物理键）。**页头下细条改为「当前光标项的完整标识行」**：文件栏聚焦显示选中文件的**完整路径**，设备栏聚焦显示 **proto://ip:port**（都是列表行里看不到的信息）；**扫描进度 / 结果改画在设备栏标题行右侧**（`Devices (3)` 右边），据此修掉"扫描信息与路径挤在同一行叠字"与"扫描提示消失时路径位置跳变"两个问题；扫描中文案同时简化为「扫描中… N/M」（"找到 N 台"列表里已可见，不必重复）
- [x] 触摸补齐（d166-d170）：定位为**按键为主、触摸为辅**——触摸只保证"**不卡死 + 顺手**"，不追求全操作对等；据此**明确不做**两件事：把页脚提示条改成可点（它是纯展示层，且位于握持区、上面恰有 Cancel / Reject / 清空等破坏性动作）、启用背面触摸板（误触多、看不见手指位置）。补上两处**触摸死锁**（进设置页只有 SELECT、无设备时扫描只有 △），并给各子页补齐触摸出口：主页右上角「扫描 / 设置」按钮；设置 / 色盘 / 接收设置 / 目录选择四页右上角「返回」按钮（动作沿用该页 ✗/方块键语义）；文件与目录两个浏览页**首行固定 `..`** 回上级（`..` 即路径语法里的"上级目录"）；目录选择页与色盘页右下角「存到此处 / 保存」按钮（后者此前触摸只能调色不能落盘）。页头按钮统一为 `w_hdr_button` 组件（40px 方框 + 居中图标 + 52×52 触摸热区）
- [x] 接收方向 TLS 化与吞吐（d172-d182）：每台设备启动生成**设备身份证书**（身份持久化），http 服务器改**单端口双栈**（首字节 `0x16` 判 TLS），announce / 自述 / prepare 统一声明 `protocol:https` + 指纹，TLS 锁 1.2、ChaCha20-Poly1305 优先；握手 447~521ms → **230~250ms**（身份解析挪到启动、握手内不打日志），重新进入官方客户端 register 的 500ms 预算。收体三层流水（解密 / sha256 / 写盘各一条线程）使接收 **2.81 → 5.21MiB/s**；发送体读/发双缓冲流水 + 窗口退避对齐使发送 **3.53 → 4.66MiB/s**。两端均已压在裸 TCP 标定上限（下行 5.43~5.54 / 上行 4.72~4.85MiB/s）
- [x] sha256 校验与接收 PIN（d178 / d185 / d186）：**发送前校验**（设置项，默认开）在 prepare 前预扫整批文件（读+哈希双线程流水 8.41MiB/s，约 12s/100MB），等待页显示按文件均分的分段进度条 + x/N；**接收时校验**（设置项，默认开）与解密/写盘并行、零墙钟成本，不符回 422 且不落正式文件。对端开了 **接收 PIN** 时，发送会弹系统键盘输入 `?pin=` 重发（≤3 次，429 提示对端忙）；接收侧 sessionId/token 改 `getentropy` 真随机
- [x] 接收侧单文件失败不再拖垮整批（d188/d189）：写盘失败 / sha256 不符 / 文件落盘失败 / 无法创建文件等**只标记该文件**，其余文件继续接收（此前任一文件出错就把整个会话判失败，后续文件全部 403，与官方行为不一致）。全部收尾后若有失败，终态显示 `Complete, N failed` + 警示色，逐文件行标红 `Failed`。**断流 / 用户取消 / 空闲超时仍是会话级**（对端已不可达，其余文件不会再开始）。配套新增 `scripts/fake-send.py` 伪发送端，可稳定构造「单文件校验失败」「中途断流」等场景
- [x] 接收确认页识别「发送方已取消」（d199）：官方客户端在"等你接受"时取消，做法是**直接关掉那条 prepare 请求的连接**（此时还没有 sessionId，`/cancel` 用不了），而 PSV 原先在等待期间不看连接，只能干等 60 秒超时。现在每 200ms 探一次连接（非阻塞 peek，TLS 的 close_notify 同样识别），对方一撤销，确认页约 0.2 秒内换成警示色的「发送方已取消请求。」并只留关闭；**超时仍是原来的「已过期」**，正常接受/传输路径不受影响
- [x] 设备身份验证（d195-d200）：发送等待页与接收确认页各加一个「验证」按钮（**仅加密连接出现**），显示 `sort(本机指纹, 对端指纹)` 直接拼接成的 128 hex——与官方 VerifyPage 同口径（不哈希、不截断）。对端指纹：发送侧取发现公告值（发送时已用证书 pin 校验过同一串），接收侧取 TLS 握手的叶证书 SHA-256。**图形模式也已落地**：左半 4×4 图标 =SHA-256(128 hex) 前 16 字节做 base-260 取预渲染图集，与官方 Icons 模式逐个一致；右半保留 8 行文本码，PC 端停在 Icons 或 Text 都能对。顺带修正 `prepare` 里写死 `"protocol":"https"` 的问题——明文发往已关加密的对端时，会让对方接收页误以为加密而点亮验证按钮

### 原 §1 实现现状（2026-09 ~ 2026-10）

- **已落地（发送方向）**：UDP 组播发现 / register 入表 → UI 选设备、浏览 ux0 选文件 → `transfer.c` 按对方 announce 的 protocol 走 HTTP 明文或 HTTPS（mbedTLS 3.6.5、锁定 TLS1.2）执行 `prepare-upload` / `upload`，带进度回写与本地取消。HTTPS 连接自动出示内嵌设备身份证书（mTLS，应对 2026 官方 Rust 内核接收端强制客户端证书），并按对方指纹锁定其证书（详见 §3 决策表）。**发送体读/发双缓冲流水**（d182，见 §4.3/§4.5）：读盘与加密发送各占一条线程，实测 3.53 → **4.66MiB/s**，已到裸 TCP 上行标定上限。**发送前 sha256 校验**（d185）：设置项 `sendSha` 默认开，预扫后把每文件 sha256 写进 `prepare-upload`；预扫同样是读+哈希双线程流水（实测 8.41MiB/s，串行只有 4.65），进度显示在发送等待页（按文件个数均分的分段进度条 + 当前文件 x/N）。**接收 PIN**（d178）：对端开了 receive PIN 时 prepare 回 401，发送线程挂起等 UI 用系统键盘输入，带 `?pin=` 重发（最多 3 次，再 401 提示 PIN 错误；429 提示对端忙）。
- **已落地（接收方向）**：对方 prepare-upload → 自动弹接收确认页（Accept / Setup 逐文件勾选 / Reject）→ upload 由 http.c 提供流读回调、receive.c 边收边写 `ux0:data/psvsend/downloads/`（先 `.psvsend.tmp` 收完改名，sha256 校验，断流/校验失败删残留，开机清扫遗留）。sha256 校验由设置项 `recvSha` 控制（d186，默认开）：开启时与写盘/解密三级并行、实测零墙钟成本；关闭后不比对也不起校验线程（用途是对端哈希实现有误时不被 422 拒收）。兼容对方无 Content-Length 的 **chunked 流式上传**（http.c 内嵌解码状态机）；同一会话内多文件由对方**并发**发起 upload，接收侧按文件独立流式收体（每文件各自 busy 状态，互不阻塞；d68 修复了 v2.1.0 起后到文件被 409 拒绝的缺陷）。取消/放弃/空闲超时等状态经快照接口给 UI 展示结束原因。**单文件失败不终止会话**（d188，与官方一致）：写盘失败 / sha256 不符 / rename 失败 / 无法创建文件等只标记该文件，其余文件继续收；全部收尾后若有失败，会话终态为 `RECV_ST_PARTIAL`（进度页 `Complete, N failed` + 警示色）。断流 / 用户取消 / 空闲超时仍是会话级（对端已不可达）。announce 已声明 `download:true`。sessionId 与每文件 token 由 `getentropy` 生成（失败回退时间种子，d178）。**确认页阶段的发送方撤销即时可见**（d199）：官方发端取消是关掉 prepare 连接，接收侧每 200ms 探活，确认页 ~200ms 内切到「发送方已取消请求。」（超时仍显示「已过期」，见下条）。

### 原 §5.5.1 字形冷启动：根因与根治（d120-d126）

**现象**：首次切到某页 / 滚动出新行时卡顿——单字形现烤成本 CJK ≈20~32ms、拉丁 ≈2~6ms；同一字形缓存后重绘几乎免费（≈5µs/字）。d38-d40 曾以"开机预热高频页字形"规避：收窄到设备列表 / 文件浏览 / 设置顶+About（≈4.3s），期间停在 **LiveArea 壁纸开屏**、字形画进隐帧但**绝不 swap**（若 swap，display 会读到 GPU 还在异步回放的缓冲，表现为"开屏后一堆页面闪过"）；全静态页面预热（d37，6 页全烤 6226ms、屏幕全黑）与逐帧时间预算预热（d33/d34，掉帧）均因代价过高被否决。

**真因（d121 探针坐实，推翻"libvita2d 内部冷插入慢"的旧推论）**：libvita2d 默认用 `vita2d_load_font_file` 开的是**文件 face**（`FT_New_Face("app0:/fonts/*.ttf")`），而字体放在 VPK 的 `app0:`——**deflate 压缩文件系统**；FreeType 每取一个**新**字形轮廓都要在包内随机读一块并解压，实测 **~40ms/字形**（同字同号对照：文件 face 43.5ms vs 内存 face 0.19ms，差 150~180×；且**与字号无关**，故"砍字号档位"无效）。libvita2d 的 atlas / FTC / 装箱本身清白，钱全花在"从 app0 读 glyf"。**方法论教训**：此前 d118/d119 探针用 `FT_New_Memory_Face` 测 freetype，与被测对象（libvita2d 的**文件** face）输入条件不一致，导致连续三轮把矛头指向 libvita2d 内部缓存。

**根治（d122）**：启动时把字体文件一次性读进 RAM 常驻（UMA 架构，无需搬显存），字体对象改走 `vita2d_load_font_mem(buf, len)`（**只存指针不拷贝，buffer 必须常驻**）。真机 `warm total` **5315ms → 65ms**（81×），`font preload done 22/22` 正常，开机到主界面总开销 ≈665ms（其中读盘 ~435ms 占大头）。

**随后清理（d123）**：预热已无意义，**删掉开屏画面与全部字形预热逻辑**（`pages_warm_all` / `ui_warm_pass` / `settings_scroll_to` / `SPLASH_BG_FILE` 等一并移除），`ui_run` 直接 `font_preload_all()` 建齐字号字体对象（`font_preload_all` 保留：它把字体对象的创建挪到帧外，堵住"渲染中途建 GPU 纹理"的隐患）。代价：读盘那 ~0.43s 无画面（黑屏），观感可接受。

**字体对象与语言地区（d124-d126）**：字体换 Noto Sans（拉丁 + CJK 简/繁/日三份地区版本，见 §5.5）。字号槽 `g_fs[]` 一次建齐 lat+cjk 两份，CJK 槽按**当前界面语言**算（`cjk_slot_current`）、**不能沿用该次调用的 `cjk` 参数**——建槽通常由"要拉丁"(cjk=0) 的那次调用触发，若沿用参数会把 CJK 也建成拉丁字体，表现为**所有汉字渲染成方块**、且 `font preload` 仍报满数（d125 修复）。换语言时在每帧 `start_drawing` **之前帧外**重建 CJK 字体对象（`font_reload_cjk`：释放旧的、按新槽 `load_slot`）——`vita2d_load_font_mem` 会建 512×512 显存纹理，落在渲染 pass 中途有 GPU crash 风险；首次切到某地区读盘 ~1.6s（16MB），之后常驻 RAM——**该 1.6s 已于 d148 在设置页内消除，见下**。

**设置页字体预读（d148）**：语言行只在设置页，故那 1.6s 只会发生在设置页内。现在**进设置页即起低优先级线程后台预读"另外两份 CJK"**（拉丁与当前语言那份本已常驻），页内切语言退化为从 RAM 建字体对象——真机实测相邻两次 `font_reload_cjk` 间隔 **1~3ms**（十次连续切换无卡顿）；**出页停线程并释放非当前语言那份**，页外常驻 ≈17MB 与从前一致，页内峰值 ≈49.9MB（真机三份同驻无 `malloc` 失败）。读盘侧加 `EMPTY/LOADING/READY` 状态机 + **CAS 抢读盘权**（预读线程与"页内切语言"的主线程可能同时要同一份，各读一遍会白占 16MB 且其中一份永远泄漏）、256KB 分块（使线程能在出页时及时收手）、**整份成功才发布**（永不存在半份 buffer）；释放顺序"停线程 → 等退出 → 才 free"，并按 `cjk_slot_current()` 只清非当前语言那份。进出走**显式钩子**——色盘页 / 目录选择页退出会把 `page` 设回 `PAGE_SETTINGS`，按"页边沿"判断会把进子页误判成离开设置页；"接收请求顶掉设置页"这条路径也在 `open_recv_request` 收尾。`font_reload_cjk` 的调用点同时由 `start_drawing` 前挪到 swap + `wait_rendering_done` 之后（换字体等待期间屏上已是新语言界面）。详见本附录。
