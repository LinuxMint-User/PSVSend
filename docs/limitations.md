# 边界与已知限制

以下为当前实现的实际边界，均来自真机验证或代码常量。设计取舍与路线见 [design.md](design.md)。

## 网络 / 发现

- **只走 IPv4、协议 v2**，不实现 v3（签名 / WebRTC / v3 的 PIN 体系）与 IPv6。注意 v2 的「接收 PIN」是支持的：对端开了 PIN 时我方发送会弹键盘输入（见「发送」第 3 步）；我方作为接收端不设 PIN（确认页就是闸门）
- **Vita 收不了 UDP 组播**：系统保留 53317（bind 报 EACCES），而 LocalSend 组播固定发往 `224.0.0.167:53317`，无法 bind 即无法收包。设备列表靠两条替代路径填充：对方主动 HTTP register（每 ~5s）+ 手动主动扫描（设备列表按 **△**）
- **主动扫描只覆盖 /24 子网**（假设掩码 255.255.255.0）：非常规子网（/16、/23 等）扫不全。扫描携带设备证书、逐 IP TLS→明文探测（2026 官方端默认 HTTPS，故 TLS 优先，明文兜底兼容纯 HTTP 端），对 HTTPS/mTLS 官方端有效（2026 版 Rust 内核要求出示客户端证书，见上）；**关加密的纯 HTTP 官方端也已实测**（d202：PSV 能扫到明文 PC，明文 PC 也能扫到 PSV）；**优先探测历史在线设备**（config `knownIps` 持久化，上限 24、LRU 淘汰），常用设备通常在轮次开始后 ~1s、进度极低时即出现；实测整轮约 6~10s（8 并发 worker），界面有进度；每轮会对未在线的 IP 全部空探一遍（无法跳过，扫描期间网络开销较低）
- **设备表 30s 无动静移除**：对方停止 announce/register 30s 后从列表消失
- **HTTP 服务器每连接独立 worker**：accept 线程只分发，一个连接一个处理线程（上限 **64**，满员时先放锁等最多 1.5 秒空槽，等不到才关闭新连接）。**跨会话忙时**（本机正在收/发文件）另一台设备的新请求**立即收到 409**（LocalSend 端显示"对方正在处理另一个请求"），不会在 TCP 队列里干等；空闲时 register/prepare 等请求不会被大文件 upload 阻塞。仍为**单活动接收会话**（一次只服务一台设备，见下）

## 接收

- 多文件接收中途取消的竞态已修复（收满优先于取消判断）：正在传的文件若已收满则保留完整、会话以「用户取消」收尾，未收满才清理其残 `.psvsend.tmp`；已收完的文件始终保留
- **接收端同一端口同时服务 TLS 与明文 HTTP**（首字节 `0x16` 判 TLS，端口候选 4567 / 53318 / …，announce / scan / prepare 统一声明 `protocol:https`）：2026 官方客户端会按 announce 走 HTTPS，纯明文端仍可互操作（明文兜底是 Web / download API 的协议要求）
- **实测吞吐已到网卡上限**：接收 **5.21MiB/s**（148.6MB / 27.2s）——收体解密、sha256 校验、写盘走三级流水并行（3×64KB 轮转缓冲，sha 与写盘各占一条线程、处理不同块），瓶颈已回到 socket 收 + TLS 解密本身；发送 **4.66MiB/s**（148.6MB / 30.4s，其中发送体 4.92MiB/s）——读盘与加密发送各一条线程（2×32KB 轮转，d182），且发送窗口没空时只让出 CPU / 退避 1ms（原 20ms）。两者分别对应下行 5.43~5.54 / 上行 4.72~4.85MiB/s 的裸 TCP 标定值（Vita socket 缓冲已是最优，调大反而更慢）。TLS 锁 1.2、密码套件优先 ChaCha20-Poly1305
- **信任是 trust-first**：服务端 `VERIFY_OPTIONAL` + 空 CA，只记录对端证书指纹、不拒绝任何对端——加密防被动嗅探，**不防主动 MITM**；**身份验证码已落地**（d195~d200：发送等待页 / 接收确认页的「验证」按钮，图标 + 文本双份比对），但它只是**人工核对手段，不改变信任决策**（不会自动放行或断开）；指纹白名单 / 接收端 PIN **未做且已暂缓**（2026-10-23 决定；Web 网页端 d208 已落地，但网页本身要求 PIN + 接收确认，不构成无人值守场景；出现该需求时只做「收藏设备自动接收」，不做全自动档）
- **同一时刻只处理一个接收会话**：正在收 / 最终化时，**另一台设备**的 prepare-upload 返回 409；**PSV 正在发送文件时同样 409**（发送中不收新文件），避免请求被晾到超时。旧会话已经结束（DONE / PARTIAL / CANCEL / FAIL / TIMEOUT）或空闲超过 120 秒且无 worker 持有时，新的 prepare 会**直接接管清场**，不必先退出进度页（d267）；**同一会话内的多个文件由发送方并发 upload**（官方客户端即如此），接收侧按文件独立流式收体、互不阻塞——后到的文件不再被 409 拒绝；会话按"所有文件都到终态"收尾（d68 修复，此前 v2.1.0 起多文件同会话传输会失败）；**单个文件的错误（写盘 / 校验 / 落盘等）只标记该文件**，全部收尾后会话显示为部分成功（d188，与官方一致）
- **清单与路径上限**：单会话 ≤2048 个文件（设置页「接收文件上限」64/128/256/512/1024/2048；文件数超过设置值时本次临时提升到最小可容纳档，不改设置）；prepare 清单 JSON ≤4MB（超 413）；相对路径 ≤512 字节、单级 ≤191 字节、深度 ≤16，最终路径按 `.psvsend.tmp` 口径 ≤1023；非法路径 / 非法 UTF-8 / 越界条目跳过并计数
- **超时三档**：prepare 等界面决定 **60s**（**确认页上无操作满 60s** 才回 403：进接收设置页 / 验证页期间暂停，回来重开满窗，确认页有操作也重开；官方客户端这一步没有超时，我们这条只为不长期占住 http worker）；接受后/文件间空闲 **120s**（判定 TIMEOUT、清理临时文件）；收体中 socket 连续 **30s** 无数据判为断流
- **sha256 校验**：接收时仅当对方提供才校验（prepare 清单里有 64 位 hex；不符回 422、不落正式文件，**只影响该文件**，同批其余文件继续收，d188），多数客户端默认带 sha256；设置页「接收时校验」可关（关掉仍照收、只是不比对）。发送时由设置页「发送前校验」控制（默认开），开启后 prepare 前先预扫整批文件（约 12 秒 / 100MB），关闭则请求里不带 sha256
- **保存目录可选**：默认 `ux0:data/psvsend/downloads/`（设置页“存储 → 保存目录”可持久改默认；接收 Setup 仅临时改本次，新请求回默认）；目录选择器复用文件浏览的 ux0 目录树（仅列文件夹、无新建目录入口）；同名文件默认在扩展名前加 `(k)`，顶层平铺文件冲突时可选择覆盖（新文件校验通过后才替换旧文件）
- **文件夹接收**：对方清单的 `fileName` 带相对路径时按原结构还原。每个顶层目录先写 `<名>.psvsend-part/`（内部直接还原子路径），收完由独立线程整体 rename，或与已有目录逐项合并（文件 `(k)`、目录合并、类型冲突跳过计数）；取消 / 强杀后启动清扫暂存根。顶层目录已存在时默认合并、可重命名 / 跳过；顶层文件可覆盖 / 重命名 / 跳过（覆盖默认不选中，新文件收完并通过 sha256 后才删除旧文件；目录合并内的同名文件仍按 `(k)` 保留，不覆盖）；嵌套同名目录被文件占用时默认重命名顶层。**空目录不会还原**（协议没有目录条目）；PSV 自己发文件夹仍不支持；仅大小写不同的入站顶层会合成一个根（FAT 不区分大小写）
- **大量平铺小文件**：单批 >64 个且单文件 ≤256KB 时直接以最终名写入，省掉每个文件的 `stat` + `rename`；代价是传输中强杀可能留下写了一半的最终名文件（不覆盖已有非空文件，重名仍走 `(k)` 避让）。用户选择「覆盖」的顶层文件不走直写，仍先写 `.psvsend.tmp`、校验通过后再替换。**目标目录很大时仍有每文件开销**：ux0 的 FAT/exFAT 按路径查找是目录线性扫描（1700+ 个文件的目录单次约 280ms），所以小文件实测约 1 秒 / 个；接受前的冲突预检已改为"一次目录遍历 + 名字查表"（32 个文件 8983ms → 650ms，d266），但落盘阶段的每文件查找未优化（8MB 单文件实测 2.64MiB/s，说明吞吐本身没问题）
- **单文件大小上限取决于文件系统**（ux0 为 FAT 系，单文件 ≤4GB-1）；磁盘写满时该文件标失败，同批其余文件若仍写得进会继续收（全部失败则显示 `N failed`）

## 网页共享

- **共享范围 = 本次已选文件**（≤2048 个），不是浏览文件系统：浏览器只能拿到文件名与大小，拿不到路径；停止共享后会话表清空、PIN 作废，旧链接回 **410 Gone**，浏览器发起的待确认 / 进行中上传也一并作废
- **支持单段 Range（206）**：下载器可以多连接并发 / 断点续传；多段 Range（`bytes=a-b,c-d`）不支持，按整段 200 回。下载器每个任务默认开 16 条连接，故并发 worker 上限设为 **64**（两任务 + 网页余量）；同时下 4 个以上文件仍可能把槽占满，此时新请求先排 1.5 秒再被拒，网页刷新一下即可
- **中断会让下载器报失败**：下载中停止共享（或读盘 / 发送出错）时，连接以 RST 断开、后续请求回 **410 Gone**，浏览器与 Gopeed 这类下载器都会显示失败而不是把截断的文件存成完整文件（它们会把 403 当"服务器连接数限制"忽略，所以这里不用 403）
- **PIN**：4 位、每次进页面重新生成、不落 config、停止共享即失效；会话绑定来源 IP。同一 IP 错 3 次 429、**冷却 30 秒后自动清零**，不必停止共享。网页刷新必须重输 PIN；下载页在同一标签页内可凭 `sessionId` 免 PIN
- **运行页在线状态靠心跳**：网页每 2 秒发 `POST /heartbeat`，PSV 按「7 秒内有心跳」判定会话与连接来源在线（传输中另有按块刷新兜底）。连接来源最多列 **4 台**（同 IP 合并，按到达顺序，不随心跳跳位），关闭页面后 7 秒内归零；浏览器把后台标签页定时器降到约 1 次 / 分钟，所以切到后台期间会暂时显示为 0，切回即恢复
- **接收确认页可直接盖在共享页上**，不必先停共享；共享仍是单接收会话，浏览器发起上传后，其他设备的 prepare 照旧回 409
- **网页上传**：文件与文件夹两个入口共用同一份清单，可混合追加（重复选择按相对路径 + 大小 + 修改时间去重）；文件夹用浏览器的相对路径作为 `fileName`，走与 LocalSend 客户端完全相同的 prepare / upload 与冲突确认流程。已选项在页面下方列出（前 8 行 + 更多），可逐项移除或全部清除；全部成功后自动清空，部分失败保留选择。再次发送前会对上一次网页会话发 `POST cancel` 释放终态，下一次 prepare 不会撞 409；若 PSV 还停在上一批的完成页，新请求到达时会自动退回网页共享页再弹确认页，退出旧进度页也不会误清新的 pending。单次合计硬上限 **2048 个文件**（prepare 清单 ≤4MB，超出回 413 并提示）；页面提示里的「当前接收上限」跟随设置，超过设置值但 ≤2048 时由接收侧本次临时提升。空文件夹不会被选中也不会上传（协议没有目录条目）

## 扫码

- **只认标准黑白二维码**：微信名片那种异形点阵 / 屏幕低亮度识别率极低；建议把手机亮度调高、让码占满取景框。预览 640×480，采集与解码分线程，按住 R 才解码（松手只预览）
- **只接受 `http://host[:port]/?pin=NNNN` 形式的分享链接**（即 PSVSend 网页共享页显示的地址）；`https`、带路径、无 PIN 的链接会判为「不是文件传输链接」
- 入口是主页肩键 L / 页头扫码按钮（`设置 › 操作 › 扫码` 可整体关掉，关闭后按钮、L 提示与细条 tips 都不显示）；扫到的链接只用于拉取清单与下载，不上传、不改对端状态
- 下载复用普通接收会话：**同一时刻只能有一个接收会话**——本机正在收 / 发文件时会提示「另一个传输正在进行」；取消 / 断流 / 空闲超时语义与普通接收一致
- 多个二维码重叠 / 太近时可能框不准；先让取景框只覆盖目标码再按住 R 最稳

## 发送

- **文件浏览入口钉死 `ux0:/`**：目录树从 ux0 根出发，无法浏览外置卡 uma0/xmc0 等分区，只能发送 ux0 内的文件
- HTTPS 目标按 announce/扫描记录的证书指纹 pin：对方换证书（指纹随之变化）时需重新发现一次设备才会刷新指纹
- **并发上传数上限 6**：接收侧 worker 池上限 **64**，6 路上传 + prepare / cancel 通知远不越界。注意取消通知是**另开一条连接**发出的，若对端连接池已被占满（如 PSV→PSV 互传），取消可能送不到对端（本侧仍会正常收尾）
- 发送期间界面取消会中止**所有在途文件**与尚未派发的文件（并向对端发一次 cancel 通知），已传完的文件保留

## 电源与待机

- **传输期间不熄屏、不待机**（d262）：发送 / 接收 / 网页下载进行中，每秒调一次 `sceKernelPowerTick(DISABLE_AUTO_SUSPEND)` 与 `sceKernelPowerTick(DISABLE_OLED_OFF)`，只续期「关闭屏幕」与「自动待机」两个计时器——**屏幕仍会按系统设置变暗**（省电），但不会关闭、不会挂起；不住锁（不用 `sceKernelPowerLock`），传输结束或空闲后一切回归系统默认，不存在忘记解锁导致常亮的风险
- 判定"传输中"的口径：发送 `XferInfo.active`；接收存在待确认请求或状态为 `READY / RECEIVING / FINALIZING`；网页下载有活动下载（空闲心跳不算）
- 真机验证（512 个 256KB 文件、约 11 分钟）：全程暗屏不熄灭、传输未中断，`watch` 心跳连续（最大间隔 2.8 秒，正常 2 秒一条）
- 不覆盖：用户主动按电源键 / 合盖休眠；也不阻止系统在**非传输**时按设置熄屏与待机

## 更新检查

- 版本真源与主源都是 **Gitee 镜像仓库的 `src/core/config.h`**：拉取后解析 `PSVSEND_APP_VERSION` 宏的字符串值（走 raw.giteeusercontent.com 直取，免 gitee.com/raw 的 302 跳转）；解析**严格认定义行**（行首 `#define`、宏名是其后首个记号、值须数字开头，d158 收紧）——注释或其它宏里出现同名 token 不会被误当成版本串；**不新增任何版本文件**——发版要改的就是 config.h 这一个宏，镜像同步自然带上，不存在多源不一致。GitHub Releases atom 仅作主源不可达时的兜底
- **检出前提**：发布新版后须把 main 同步到 Gitee 镜像（epix-xhan/PSVSend），真机才检得出新版本——release 发布本身不会让 PSV 看到
- 自动检查默认每周（设置页可改每天 / 每月 / 关闭），检查结果只提醒、不自动下载
- PSV 无实时钟：自动周期用远端响应头 `Date` 授时，上次检查时间存 config `updateLast`（网络 unix 秒）；开机后每会话只做一次轻量判定，未到周期即静默跳过，到周期才完整检查
- 同版本或无新版显示「已是最新」；有新版显示版本号并引导到 Releases 下载；网络 / 镜像不可达时报检查失败，不影响使用

## 界面显示

- **界面内嵌字体**（随 VPK 打包到 `app0:/fonts/`，源为 Google **Noto Sans**，SIL OFL 1.1）：拉丁 `NotoSans-Regular.ttf` + CJK 按界面语言取地区版本 `NotoSansCJKsc/tc/jp-Regular.otf`（简 / 繁 / 日，各约 16.4MB，都含全部 CJK 字形，差别只在同一码位默认取哪个地区的字形）；ASCII/Latin-1 与通用标点（省略号 U+2026、弯引号等——CJK 字库缺而拉丁字库含）走拉丁字体，其余走 CJK 字体，中英文（及日文）正常显示；字库缺的生僻字符（emoji、个别扩展区）由 freetype 栅成空框或留空，传输本身不受影响。字体从内存建（启动一次性读盘到 RAM）根治了字形冷启动卡顿；d148 起**进设置页会后台预读**另外两份 CJK，页内切语言不再等读盘、出页即释放，见 [design.md](design.md) §5.5 / §5.5.1

- **验证页图标是预渲染图集**（`app0:/fonts/verify/icons-48.png`，800×850，260 格 48px + 1px 透明边，约 98KB）：不走图标字体是因为 libvita2d 的字形缓存是固定 512×512 单页且永不淘汰（260 个图标在 32px 就必然溢出，溢出**静默不画**），且它的 UTF-8 解码不认 4 字节码位（官方字母表里有 45 个图标在 U+FFFF 以上）。图集由 [scripts/gen-verify-icons.py](../scripts/gen-verify-icons.py) 按**官方字母表顺序**生成，脚本内置 260 项名字与码位（顺序即下标）并自检覆盖；图集只存灰度 + alpha，启动时帧外建纹理、常驻只读（1:1 绘制 + POINT 采样），加载失败只打日志并退回纯文本半区。**图集与官方 1.18+ 的字母表绑定**：官方若调整图标表，必须重跑脚本，否则同一 digest 会画出不同图标

## 已知小问题

- 进设置页会后台读盘两份 CJK（各 ~1.6s、合计 ~3.3s，低优先级线程，不挡界面与按键）；停留不足 3.3s 就退出的话这次读盘算白做，下次进页重新读——这是"页内切语言不冻结"的代价。页内峰值内存 ≈49.9MB（拉丁 + 三份 CJK 同驻），出页即回落，见 [design.md](design.md) §5.5.1
- 改名相关交互已实装：接收设置页每行可改保存名、设置页主机名可直接改设备名（均接 PSV 系统键盘，中文/符号全键盘输入可用，见 [changelog.md](changelog.md)「附录：实现细节」）
