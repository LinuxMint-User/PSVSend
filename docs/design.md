# PSVSend 设计文档

> 面向 PS Vita 的 LocalSend 协议（v2）兼容客户端。本文件记录前后端架构、关键决策、实现约束与开发验证。

## 1. 项目目标

- 在 PSV 上实现 LocalSend v2 兼容客户端，与局域网内其他 LocalSend 设备（手机 / PC）互相收发文件
- 协议目标 **v2**（理由见 §3）：v1 已废弃；v3 的签名 / WebRTC / PIN 体系复杂，PSV 资源有限，且官方客户端同时兼容 v2/v3，v2 生态覆盖最广

### 现状（2026-11）

| 领域 | 状态 | 关键实现 |
|------|------|----------|
| 发送 | 已落地 | UDP announce + 对方 register；`prepare-upload` / `upload`；HTTP / HTTPS（mTLS）；1-6 路并发；发送前可选 sha256 |
| 接收 | 已落地 | 确认页勾选 / 改名 / 选目录；文件夹按相对路径还原（暂存根 + 独立线程最终化）；≤2048 文件 / 4MB 清单；顶层目录冲突可合并 / 重命名 / 跳过，顶层文件可覆盖 / 重命名 / 跳过；单端口双栈；三级流水；单文件失败隔离；可选 sha256 |
| 发现 | 已落地 | 收不了组播，靠对方 register + **△** 主动扫描 /24；历史 IP 优先；公告错峰 1s / 2s |
| 安全 | 已落地 | 设备身份证书（mTLS）+ trust-first；发送等待页 / 接收确认页「验证」（文本 + 图标）；白名单 / 接收 PIN 暂缓 |

| 界面 | 已落地 | 6 种语言；Yaru / OLED / 自定义；两栏主页；按键 + 触摸；按住 R 展开提示；列表惯性 |
| 更新 / 存储 | 已落地 | Gitee 主源 + GitHub atom 兜底；config 单文件；保存目录可选 |

## 2. 总体架构（前后端分层）

```
┌─────────────────────────────────────┐
│  前端层（UI）：vita2d 界面             │ 只负责展示与交互
│  设备列表 / 文件浏览 / 弹窗 / 进度     │
└───────────────┬─────────────────────┘
                │ 调用 api.h 接口 + 后端回调事件
┌───────────────┴─────────────────────┐
│  后端层（协议核心）：                 │ 纯逻辑，不碰 UI
│  UDP 发现 / HTTP 服务器 / HTTP 客户端 │
│  会话管理                            │
└───────────────┬─────────────────────┘
                │ 系统 API 调用
┌───────────────┴─────────────────────┐
│  底层：SceNet / SceIo / SceLibJson /  │
│        SceKernelThreadMgr（系统固件） │
│  + vita2d / freetype / mbedtls（第三方）│
└─────────────────────────────────────┘
```

- 底层能力（socket、文件 IO、JSON、线程、GPU）由 **PSV 固件系统库**提供真实实现；**vitaSDK** 提供头文件、stub 库（链接通道）与 newlib（标准 C 库）
- 前后端通过 **api.h 契约**解耦：后端不关心按钮怎么画，前端不关心协议细节，可独立开发与验证

## 3. 关键决策

| 决策 | 结论 | 理由 |
|------|------|------|
| 协议版本 | **v2** | v1 废弃；v3 复杂（nonce 签名 / WebRTC），官方保持 v2 向后兼容，生态主流是 v2 |
| 传输 | HTTP 明文与 HTTPS 双支持，按对端 announce 的 protocol 自动选择 | 明文互通无碍；对端为 https 时必须加密 |
| TLS 方案 | **mbedtls**（工具链自带 3.6.5），锁定 TLS1.2 | PSV 系统 SceSsl 对 homebrew 不可用；TLS1.3 的证书校验不走 per-cert 回调，指纹 pin 依赖 1.2 |
| HTTPS 信任模型 | 对端证书按 announce 指纹 SHA-256 **pin**（VERIFY_OPTIONAL + 自管校验回调），不依赖 CA 链 | LAN 内无公开 PKI；协议本身即以 fingerprint 标识设备 |
| mTLS 客户端身份 | 内置自签 RSA-2048 设备证书（`identity.c` + `id_cert.inc` / `id_key.inc`），对端强制客户端证书时自动出示 | 2026 官方 Rust 内核接收端对非浏览器发送方强制客户端证书，无证书即 `certificate_required` 握手失败 |
| 接收方向 TLS | **单端口双栈**：worker 读首字节，`0x16` 走 mbedTLS 服务端握手，其余按明文 HTTP；服务端出示同一张设备身份证书，TLS 锁 1.2、ChaCha20-Poly1305 优先 | 对方按 announce 的 protocol / port / fingerprint 直连，端口不能变；明文兜底是 Web / download API 的协议要求 |
| 服务端信任模型 | `VERIFY_OPTIONAL` + 空 CA，`srv_verify` 只记录对端证书指纹、不拒绝（trust-first） | LAN 无公开 PKI，先保证"加密防被动嗅探"；白名单 / 接收 PIN 后置（§9） |
| HTTP/1.1 范围 | **子集**：POST、Content-Length、**chunked 解码**、query string；响应后关闭连接 | 目标是"兼容 LocalSend"，非"完备 HTTP"。chunked 必须支持（官方 Dart 客户端可能使用）；**不支持 multipart 编码**（v2 多文件逐 POST 单文件裸流，见 [limitations.md](limitations.md)）；解析器独立模块、防御式实现（全部读取设上限、不支持格式优雅拒绝 400） |
| 内存约束 | 按 **256MB** 设计基准（实际预算 365MB 封顶） | 512MB 为**统一内存**（CPU/GPU 共享），系统保留约 147MB，应用可拿最大 365MB（工具箱可调 256/285/333/365） |
| 文件处理 | **大文件永不整读入内存**，一律流式（收：边收边写盘；发：边读边发） | 内存红线 |
| 传输分块 | 16~64KB 缓冲 | PSV socket / sceIoRead 的大块缓冲限制 |
| 应用数据目录 | `ux0:data/psvsend/`（含 `downloads/` 接收目录），首次启动 `sceIoMkdir` 幂等创建 | 符合 PSV 惯例，homebrew 有写权限 |

### 4.2 核心数据结构

- **设备表**：`Device[]`（发现线程维护，mutex 保护），含 ip / port / alias / fingerprint / protocol / last_seen。
- **接收**：`PendFile[]` / `RFile[]` 按清单实际数量动态分配（≤2048，勾选用 bitset）；每个目录型顶层一条 `SessRoot`（最终名 / 暂存根名 / 文件数）与 0 字节文件表。UI 只拿 `RecvPendingSummary` / `RecvStatusSummary` + **64 行窗口**，不整份拷贝。
- **发送**：`XferFile[]`（`XFER_MAX_FILES` 仍为 64 条），进度由 `XferInfo` 锁内快照。
- **状态**：`AWAIT_CONFIRM → TRANSFERRING → FINALIZING`（仅接收）`→ DONE / PARTIAL / CANCELLED / FAIL`。

### 4.3 线程模型

| 线程 | 职责 |
|------|------|
| UI 主线程 | 渲染 + 消费事件队列刷新界面 |
| 发现线程 | UDP recvfrom 循环 + 定时发 announce |
| HTTP 服务器线程 | accept 循环，**每连接一个工作线程**（LocalSend 并行传多文件）；工作线程内先做 **TLS / 明文嗅探**（首字节 `0x16`），TLS 连接现场做服务端握手 |
| 收体流水线线程（recv） | 每个 upload 起两条（对端给了 sha256 且设置项 `recvSha` 开时）或一条：生产者只做解密 / 攒块，**sha 线程**只算校验和，**写盘线程**只 `sceIoWrite`；3×64KB 轮转缓冲 + `sem_free`/`sem_sha`/`sem_job` 计数信号量，块逐级传递、sha 与写盘处理不同块（d180，三级流水） |
| 最终化线程（recv，M2） | 全部文件到终态后置 `FINALIZING`，由独立线程**在锁外**补建 0 字节文件、逐根 `rename` 或合并（文件 `(k)`、目录合并、类型冲突跳过计数）；完成回锁置 DONE / PARTIAL / FAIL，失败保留暂存根等下次启动清扫 |
| 发送线程（xfer） | `prepare-upload` 一条连接等对方决定；接受后起 N 个 worker 线程并发上传（N = config `maxParallel`，上限 6），join 完全部 worker 后**统一写一次终态**（见 [changelog.md](changelog.md)「实现细节」）。每个文件另起一条**读盘线程**，worker 本线程只做 `mbedtls_ssl_write`：2×32KB 轮转缓冲 + `sem_free`/`sem_full` 计数信号量，读满声明 size（或读失败）投 `len=0` 终止块（d182，读/发双缓冲流水） |
| 预扫线程（xfer，d185） | `prepare-upload` 之前按文件顺序算 sha256（设置项 `sendSha` 默认开）：一条读盘线程 + xfer 线程自身做 `mbedtls_sha256_update`，缓冲结构与发送侧同一套（2×32KB 轮转）。每条线程各自跑满（读 9.7 / 哈希 8.8MiB/s），合流实测 8.41MiB/s |
| 定时器（可并入发现线程） | 设备超时清理、announce 周期触发 |

共享数据（设备表、会话表）统一 mutex 保护。

### 4.5 HTTP 服务器要点

- 路由：`/api/localsend/v2/register`、`prepare-upload`、`upload`、`cancel`、`info`
- `prepare-upload` → 生成 sessionId，为每文件分配 fileId + token，返回 `{sessionId, files:[{id, token, fileName, size}]}`；同时向 UI 抛"待确认"事件
- **prepare 清单体**：请求头仍读进 32KB 缓冲；声明了 `Content-Length` 时按它堆分配（**4MB 硬上限**，超 413；读短 / 超时 400），handler 返回后才 `free`；无 CL 保留旧的“32KB + 空窗判完”兼容路径。`chunked` 明确 411；同一时刻只允许一个 prepare 体，忙则 409。回执按文件数动态分配（1MB 上限，越界 507，绝不发半截 JSON）。拒绝原因合并成一次性事件，主页细条用危险色显示 8s
- `upload?sessionId&fileId&token` → 校验会话与 token 匹配 → 流式写盘（平铺文件先写 `*.psvsend.tmp`，目录型文件写 `<顶层>.psvsend-part/<相对路径>.psvsend.tmp`，完成后 rename；同名加序号避免覆盖）。路径在 prepare 阶段按 `recv_path` 净化并做预算检查，非法 / 超长条目跳过计数
- **数量上限**：单会话 ≤2048 文件（设置页 6 档，超过设置值但 ≤2048 时本次临时提升）；相对路径 ≤512 字节、单级 ≤191 字节、深度 ≤16、最终路径按 part 口径 ≤1023
- **单文件失败隔离**：写盘 / 校验 / 落盘错误只标记该文件，全部到终态后会话收尾为 PARTIAL
- **安全底线**：只收"prepare 过"的 fileId+token，否则 400；拒绝时回 401/403
- **单端口双栈**：工作线程先 `sceNetRecv(fd,p,1,0)` 读首字节，`0x16` → mbedTLS 服务端握手（失败即关连接），否则把该字节塞回 `Conn.p` 按明文 HTTP 解析（`conn_read` 先吐缓存，不丢包）。端口候选与 announce 不变，`protocol` 改声明 `https`
- **服务端身份与信任**：出示 per-device 自签 RSA-2048 设备证书（§3），`VERIFY_OPTIONAL` + 空 CA；`srv_verify` 只把对端证书 SHA-256 记到 `Conn.peer_fp`，不中断握手（trust-first，白名单 / 验证码的判定点就留在这里）。身份解析全局缓存一次 + 启动预热，**握手路径内不写 dlog**（同步写盘几十毫秒，会挤爆官方 register 的 500ms 预算）
- **吞吐**：收体走三级流水（解密 / sha256 / 写盘各一条线程，§4.3），实测 **5.21MiB/s**（148.6MB / 27.2s）；瓶颈是 socket 收 + TLS 解密本身（等价 ~5.58MiB/s）。发送方向走读/发双缓冲流水（d182，§4.3），实测 **4.66MiB/s**（148.6MB / 30.4s，发送体 28.8s = 4.92MiB/s），已达**裸 TCP 上行标定上限**（d181 专项测试：上行 4.72~4.85、下行 5.43~5.54MiB/s，socket 缓冲已最优、调大反而更慢）。两端都到顶（标定方法见 §4.3 / d181 专项测试：裸 TCP 双向灌流）
- 接收文件写入运行时保存目录（默认 `ux0:data/psvsend/downloads/`，UI 可选：config `saveDir` 持久 / 接收 Setup `recv_dir` 仅本次，见 [changelog.md](changelog.md)「实现细节」）
- **并发连接与网页路由**：每连接一个 worker（上限 `HTTP_MAX_CONN = 64`，满员放锁等最多 1.5s 空槽再拒）。上限按"下载器每任务 16 条连接 × 两个任务 + 网页余量"取整；提高会让线程栈（每连接 0x40000）与下载缓冲（64KB）线性增长，不再随客户端继续上调。`GET /`、`prepare-download`、`download`、`heartbeat` 四个网页路由与 LocalSend 路由共用同一监听端口（明文 HTTP，不分 TLS）

### 4.6 HTTP 客户端要点

- 流程：register（可选）→ `prepare-upload` 拿 session（只有这一条连接）→ N 个 worker 并发 `POST upload`（协议 §4.2 明示 `This route can be called in parallel.`）→ cancel 清理
- 按**接收端 announce 的 protocol / port 字段**决定 http/https 与端口——明文即可互通
- 上传：32KB 分块，**读盘与加密发送各一条线程**（2×32KB 轮转 + 信号量，d182）；发送窗口没空时先让出 CPU 8 轮、再退避 1ms（原文 20ms，约四成块会撞一次）。**每个文件一条连接**，故每文件各做一次 TLS 握手（N 并在途，握手也并行）
- **发送前校验**（d185）：设置项 `sendSha` 默认开时，`prepare-upload` 之前先按文件顺序预扫 sha256（读+哈希双线程，8.41MiB/s ≈ 12s/100MB），结果逐文件写入请求的 `sha256` 字段；关闭则字段为 `null`，与旧版行为一致。预扫进度显示在发送等待页（按文件数均分的分段进度条 + x/N），可按 ○ 取消（此时 prepare 尚未发出）
- **接收 PIN（d178）**：`prepare-upload` 回 401 表示对端开了 receive PIN——发送线程置 `pin_need` 并挂起（≤120s），由 `pages_tick` 弹系统键盘，输入后带 `?pin=`（RFC3986 百分号编码）重发，最多 3 次；再 401 报「PIN 错误」，429 报「对端忙」。PIN 只在本次发送线程内保存，不落盘
- 失败分级：HTTP 4xx/5xx / 无 token / 读文件失败 = 单文件失败（其余继续）；连不上 / 握手失败 / 断流 / 等不到回执 = 连接级失败 → **全局中止**（详见 [changelog.md](changelog.md)「实现细节」）
- **扫码拉取（`net/httpc.c`，d229-d233）**：独立的**明文** HTTP 客户端，不依赖 TLS / transfer 的发送链路——非阻塞 connect + 轮询收发，适配 Vita 没有可用的阻塞式高层客户端这一现状。`prepare-download?pin=` 取 JSON 清单（官方 web share 返回 map、我们自己的返回数组，`json_util` 两种都能读），`download?sessionId=&fileId=` 按 64KiB 流式回传；只服务扫码下载（主页扫码入口），不做通用 HTTP 客户端

### 4.7 实现顺序与验证

1. `net.c` 网络初始化（跑通不崩）
2. `discovery.c` 发现 + 设备表 → **PSV 上能看到手机/电脑设备**
3. `http_server.c` prepare-upload + upload 收文件 → **电脑 curl 模拟 LocalSend 对测**
4. `session.c` 状态机 + 确认/取消
5. `http_client.c` 发送 → **官方 LocalSend App 真机对测**

### 4.8 Web 网页端（web share，d208-d260）

官方 LocalSend 的 web share 口径：别人用浏览器打开 PSV 的地址即可下载本次分享的文件，或把文件发到 PSV。定位是**局域网内的临时入口**，不是文件服务器。

- **形态**：单个明文 HTTP 端口（与 LocalSend 同端口，TLS 只服务 LocalSend 客户端），网页（HTML/CSS/JS）编译进固件、不读外部 assets；英文打底，运行时按 `navigator.languages` 选简中 / 繁中 / 日文。两模式互斥：下载模式（分享本次已选文件）与上传模式（浏览器发文件或整个文件夹给 PSV）。上传页的文件与文件夹是两个选择入口、共用底部发送按钮，**可混合追加到同一份清单**（按相对路径 + 大小 + 修改时间去重）；已选项以列表展示（前 8 行 + 更多），支持逐项移除与全部清除，全部成功后自动清空。再次发送前会 `POST cancel` 释放上一次已完成的网页会话，避免下一次 `prepare-upload` 撞 409。
- **路由**：`GET /`（单页）、`POST /api/localsend/v2/prepare-download?pin=`、`GET /api/localsend/v2/download?sessionId=&fileId=`、`POST /api/localsend/v2/prepare-upload?pin=`（复用接收链路）、`POST /heartbeat?sessionId=`（204，仅续在线时间、不计数不打日志）。
- **会话与 PIN**（`net/web.c`，一把互斥锁串行）：`sessionId` 32 hex（`getentropy`），槽位 4、满了淘汰最老；PIN 4 位、每次进页面重新生成、不落 config、停共享即失效；会话绑来源 IP（不符回 403）。同一 IP 错 3 次起 429，**冷却 30 秒后自动清零**（否则输错一次就得回 PSV 停共享）。下载页把 `sessionId` 存 `sessionStorage`、刷新可免 PIN；**上传页不缓存任何凭据，刷新必须重输**。
- **流式下载**：`sceIoOpen` + 64KiB 块 `conn_write`；`Content-Disposition`（ASCII 回退 + RFC 5987），64 位 `Content-Length`。**单段 Range**（`bytes=a-b` / `a-` / `-N`）回 206 + `Content-Range`，多段与越界按整段 200 回——支持 Range 是为了让 Gopeed 这类下载器走多连接路径（其单连接路径读错只标 `connFailed`，最终仍判"已完成"）。
- **中断语义**：下载中停共享 / 读盘或发送出错时，没发满 `Content-Length` 就设 `SO_LINGER{on,0}` 让 close 发 **RST**，后续请求回 **410 Gone**（共享已停 / 会话失效）：只发 FIN 时浏览器可能把截断文件存成完整文件；而 403 会被 Gopeed 当成"服务器连接数限制"忽略，所以不用 403。IP 不符仍用 403。
- **在线状态**：网页每 2 秒 `POST /heartbeat`，PSV 以「7 秒内有活动」判定会话与连接来源在线（传输中每 64KB 也刷新）；关页后 7 秒内归零。连接来源最多记 **4 台**（同 IP 合并，按到达顺序、心跳不改变位置；槽满挤掉最久没活动的、新设备排末尾），运行页逐行显示，行数与宽度按卡片边界裁剪，超出用 `+N` 提示。
- **并发**：worker 上限 64（见 §4.5）。下载器每任务默认开 16 条连接，两个任务 32 条 + 网页请求仍有余量；4 个以上任务同时下载才可能占满，满员时新连接先等 1.5 秒空槽再被拒。
- **上传面板**：PIN 后分「选择文件」「选择文件夹」两个独立入口（文件夹输入 `webkitdirectory`，用 `webkitRelativePath` 作为 `fileName`，接收侧按相对路径还原）。客户端按 **2048** 硬上限拦截并提示；面板下方显示当前接收上限（`recv_files_limit`，共享开始时注入页面，超出设置值但 ≤2048 时由接收侧本次临时提升）。prepare 的 413 / 409 / 507 分别提示“文件过多或清单过大 / PSV 正忙 / 内存不足”，不上传半截。
- **UI**（`PAGE_WEB`）：三个入口——主页 START（已选 >0 直接开分享）、页头地球按钮、设置 › 操作 › 网页共享。选择态列出将分享的文件；运行态显示 URL / PIN / 模式 / 会话数 / 来源列表 + 圆形长按按钮。**停止共享改为长按 0.7 秒**（按钮或返回键，短按无效；触摸蓄满后抬手不再合成 tap），替代原来的确认弹窗。
- **与接收模块的衔接**：浏览器上传走同一条 `prepare-upload`，用 `via_web` 标记来源（带有效 PIN 才算），确认页可直接盖在共享页上（`pages_tick` 的可打断页加入 `PAGE_WEB`）；停共享时 `web_stop()` 后 `recv_cancel_web()` 作废网页发起的待确认 / 进行中上传。确认页收尾按 `return_from_recv()` 回到来源页（共享页仅在仍运行时回到共享页）。
- **不做**：目录浏览、多段 Range、打包下载；浏览器后台标签页定时器降频（约 1 次 / 分钟），切到后台期间在线状态会暂时显示为 0。

### 5.2 架构：事件驱动 + 状态机

```
主循环（每帧）:
  poll 输入（按键/触摸） → 处理当前页交互
  → 消费后端事件队列（设备变更/收件请求/进度）
  → 渲染当前页 → 帧同步
```

- 后端回调**只塞事件队列**（EV_DEVICES_CHANGED / EV_INCOMING_REQUEST / EV_PROGRESS），主循环消费，线程安全不卡渲染
- 页面为状态机：`enum Page` + 每页自己的选择状态

### 5.3 双输入：按键 + 触摸统一模型

- **输入抽象层**：页面只处理抽象动作 `UiAction`（CONFIRM / CANCEL / UP / DOWN / LEFT / RIGHT / BACK / MENU），不判断物理键
- **按键路径**：十字键移动焦点，确认键触发焦点控件
- **触摸路径**：坐标命中检测 → 触发控件动作
- **控件统一**：`{ Rect bounds; UiAction action; void *target; }`，两种输入源最终走同一 action；可混用
- **确认键布局可配置**：美式（X=确认，默认，港版/国行习惯）与日式（O=确认），存 config；触摸不受影响。切换入口是该行自己的**选项面板**（d145/d146）——确认键只负责"开面板 / 应用"、不参与选档，故"用确认键改确认键"的自指负担自然消失（早期为此单开左右方向键，已废）
- **设置页值行 = 右侧选项面板（d145/d146）**：值行点整行（焦点行按确认同理）→ 右侧滑出 320px 面板（列表行宽 912→576、150ms 动画，面板态隐藏滚动条），↑↓ 选档（到顶 / 到底把那一臂画灰，**不循环**）、确认 = 应用并落盘（**面板不收起**，便于连试几档）、✗ 或点面板外 = 关且不应用；面板态拖动滚动冻结、列表焦点不动、其余按键吞掉。2 档同样走面板（交互统一）；动作行不适用（点了直接执行）；OLED 下「外观」行无档位、页脚确认段画灰。页脚文案与实现见 [changelog.md](changelog.md)「实现细节」
- **页脚提示条独立成模块（`src/ui/hintbar.c/.h`，d106）**：页面只声明"本页用到哪些键、文案、状态"（`HintSeg` 数组），**不关心顺序**；排序、图标选择、排版只在 hintbar 内实现一处，加新按键只需补 `HintKey` 枚举与 `icon_of` / `rank_of` 两张表，各页面零改动。段结构：`key`（+ 可选 `key2` = "两个键同一动作"，画成「键 `/` 键 文案」，两个键都画出、动作文案只写一次）、`text`、`dim`（动作当前不可用 → 灰字灰图标）、`varies`、`dir_off`。**图标由键推出**（`icon_of`：`HKEY_CONFIRM` / `HKEY_BACK` 按当前键位布局在 ○ / ✗ 间取），页面不写图标，消除"键与图标对不上"的非法组合。**可选蓄力环（d159~d165）**：页面在 `w_page_footer_segs()` 之前调 `w_page_footer_charge(key, pct)`，给该键所在段的图标外画一圈进度环（pct 0~1，0 = 不画），绘制后自动清除（与 `w_clear/w_add` 同模式）——`HintSeg` 不增加动画字段，不给全仓共享结构塞一次性渲染参数
- **排序规则（hintbar 内强制，d106/d107）**：默认键序 `SELECT、START、L、R、方向键（、…）、○、✗、□、△`——先按它排本页**存在**的键，再按**不可变靠左、可变靠右**微调。"可变"（`HintSeg.varies`）只指**动作随焦点 / 运行状态改变**的段（主页 `Send↔Remove` / `Scan↔Hold to clear all`、进度页 `Cancel↔Done`、文件页 `Select all↔Deselect all`），这类整段右移；✗ 的 `Up/Back` 只是文案随层级换词、动作恒定 → 不算可变，仍按默认序排在 □ 之前。**合并段取两键中靠前的排序位定位，段内两个图标也按同一键序排列**（`seg_rank` / 段内按 rank 交换）——内部图标顺序与整段位置都不随键位布局左右跳。○ / ✗ 两项**按图标符号**定位（○ 恒在 ✗ 前），直接后果：**美式布局下"返回(○)"排在"确认(✗)"之前**，日式布局与旧版相同
- **提示条口径**：① 确认键段文案**跟随当前焦点动作**，不写死（接收确认页固定写 "Accept" 会在焦点移到 Reject / Setup 时撒谎）；② 固定不变的提示靠左、随焦点 / 状态变化的靠右；③ `HKEY_NONE` 必须为 0、`dir_off`（`HDIR_*` 位掩码，**0 = 四向全亮**）也以 0 为全亮——全仓按 `= { 0 }` 零初始化，反例会让未改动的页面凭空多出图标或灰臂
- **页脚溢出与按住 R 展开（d224-d226，d240 校正 R 段归属）**：**不再压缩字号、也不按"两行宽度最接近"硬折**（那会让第二行像上一行掉下来的半句）。默认单行按默认键序**整段**填充：放不下的段整段丢弃（不裁字）。R 段采用**页面声明优先**：页面自己给了 `HKEY_R` 段（主页就是这样）就按页面声明画，模块不再自动补；页面未声明且**确有段被丢弃**时，才自动补一条（`HKEY_R`，按默认键序排在 START 之后，**不固定在右端**）。文案在「更多提示 / 更少提示」间切换——两条文案刻意等长（简繁 CJK 与日语假名定宽差 0，英文仅 M/L 字宽几像素），保证 `fit_count` 结果不随按住状态变化，第一行不会再有段被挤进第二行。**按住 R**：页脚 46 → 92px，全部段按原顺序分两行显示，第二行从屏幕下沿滑入；动画与设置页选项面板同口径（150ms、按真实时间步进、每帧至少 1px 保证收敛）。页脚是**向上生长覆盖列表底部**，`LIST_BOTTOM` 等布局常量不变（未让列表整体上移，避免改 20 余处布局点）；第二行 y 固定在 `f.y + 50`，未展开时落在屏幕外，因此无需裁剪即可实现滑入。松开 R 立即收回，R 段文案同时切回「更多提示」。**为什么必须是"页面声明优先"**：简中 / 繁中文案短，主页页脚根本不溢出，若只按"溢出才补"主页永远看不到 R 提示；反过来若无条件补，设置页等**没用到 R** 的页面会出现一个按下去毫无反应的死提示。早期试过给页脚加"强制显示 R"开关，被否——那是把页面语义塞进纯展示模块。
- **触摸惯性滚动（d234-d237）**：所有可滚动列表共用 `ScrollGlide`。输入层在**抬手帧**给出 `drag_end` + `fling_vy`（相邻帧位移 / 间隔，指数平滑；抬手前停顿 >120ms 记 0，免得缓慢拖动后突然一滑），页面在 render 里按真实 dt 积分：由 150 px/s 启动、2600 px/s 上限、140ms 时间常数衰减、<60 px/s 收尾。**碰边硬停、不回弹**（用户明确先看"边缘硬停"的手感）；点按、按键、打开选项面板、离开页面都立即停，切页回来按 dt > 200ms 直接收尾以免跳一大截。惯性属于输入层产出的速度量，页面只做积分，不自己猜拖动方向。
- **页头按钮按住 R 展开文字（d238-d240，d242 扩到四个）**：主页右上四个按钮平时只有图标，**按住 R** 时逐个变宽并换成对应文字（扫码 / 网页共享 / 扫描 / 设置）。`w_hdr_button_var(x, w, id, kind, label, p, dim)` 在 p < 0.5 画图标、p ≥ 0.5 画文字（0.8 号字、居中、超宽裁尾），宽度按**当前语言实测**（0.8 号字宽 + 20，上限 140px），不写死。布局**右端锚定**，展开时从右往左依次让位（20ms 错峰、总时长 220ms、ease-out），标题不被挤动；收起 150ms。dt > 200ms（卡帧 / 切页回来）直接落位。文案测量按 `i18n_lang()` 缓存，换语言重建；渲染 pass 内不新建字体槽（0.8 档已在 `UI_FONT_SCALES` 预载）。
- **十字键提示 = 方向可用性指示**：`HintSeg.dir_off` 是"当前按不动的方向"位掩码（0 = 全亮），列表滚到顶/到底时对应方向变灰，用户一眼可知"这个方向按了没用"；灭臂判断**复用各页既有的移动逻辑**（如设置页 `slot_step(sl,-1)==sl` 即"上按不动"），不另写边界判断，保证提示与实际行为一致
- **触摸路径补齐（d166~d170）**：**定位 = 按键为主路径、触摸为辅助**——触摸只承诺"**不卡死 + 顺手**"，**不追求全操作对等**。据此**明确否决**两件事：① 把页脚提示条（hintbar）改成可点——它是纯展示层，改可点要吐每段 `Rect` 热区、再定义"哪段可点 / 长按怎么办"，且页脚位于**握持区**、上面恰有 Cancel / Reject / 清空已选这类破坏性动作、单段目标过小；② 启用**背面触摸板**（误触多、看不见手指位置、无视觉反馈）。本次修掉两处**触摸死锁**（"必经之路被堵"，属缺陷不属取舍）：进设置页只有 `SELECT`（全应用唯一入口）、无设备时不能扫描（设备栏 △ 短按独有，此时页面上无任何可点之物）。落地：① 主页页头右上角「扫码 / 网页共享 / 扫描 / 设置」四个按钮（网络扫描进行中画灰且**不注册热区**）；② 设置 / 色盘 / 接收设置 / 目录选择四页页头右上角「返回」，动作**沿用各页 ✗/方块键既有语义**（`settings_leave` / `cp_cancel` / `rs_leave` / `dpick_exit`），不自创；③ 文件与目录两个浏览页**首行固定 `..`** 上级项（`..` 是路径语法里的"上级目录"；在 `files_load` 插入一处，两页共用 `g_app.files[]` 零改动获得回上级能力，光标默认落 `..` 之后第一项；空目录时页脚「选择 / 打开 / 全选」按**真实条目数**画灰——`..` 不计入内容）；④ 目录选择页 / 色盘页右下角主按钮「存到此处 / 保存」——**必须画在页脚之后**（页脚整条铺不透明背景，先画会被整块盖住）。共享组件 `w_hdr_button(cx, id, kind, dim)`：40px 方框 + 居中图标 + 52×52 热区（顶满页头高），`dim` 时画灰且不注册热区；返回箭头图标 `w_icon_back`（尖头两臂 + 横杆，避免空尖头被读成小于号）。触摸热区 id 分区：页头按钮 `0x82xx`、浏览页右下主按钮 `0x90xx`（`WID_FILES_DONE` / `WID_DIRPICK_SAVE` / `WID_CP_SAVE`）。**页脚提示条保持纯展示**、不注册热区。**明确不处理（"能绕但繁琐"，非死锁）**：文件栏「按住清空已选」（可逐行点 ✕）、文件选择页「全选 / 取消全选」（可逐行勾）、目录选择页 `□ Exit`（可 ✗ 逐层退）。**已知语义割裂**（将来若改走"当触屏应用做"再一并处理）：触摸点文件栏**不切焦点** → 页脚仍显示设备栏提示；主页点设备行**直接发送**、点文件行只移动选中（与按键"选中 + 确认"两套语义并存）

### 5.4 主题系统（theme.c）

- 主题 = 一组颜色常量（bg / card / accent / accent_text / text / text_dim / border / success / danger / warn / overlay），UI 绘制只引用主题变量（**UI 层零硬编码颜色**），**运行时可切换，下帧生效**
- 内置主题在**两个正交轴**上组合：色系（`ThemeId`：Yaru / OLED / Custom）× 明暗（`THEME_DARK` / `THEME_LIGHT`），色值表 `themes[色系][明暗]`，`theme_set(id, mode)`；config 存 `theme`（色系）+ `lightMode`（明暗），设置页对应「主题」「外观」两行。自定义即色系列加一项（Custom），明暗自动正交
  - **OLED**：纯黑 `#000000` 底 + 卡片 `#111111` + 白字高对比（PSV1000 OLED 最佳）；定位纯黑高对比，**无浅色变体**（`theme_set` 对它恒定走深色档，设置页「外观」行显示"深色（固定）"且不可改）
  - **Yaru**：深灰底 + Ubuntu 橙 `#E95420` 主色 + 圆角扁平卡片（vita2d 矩形拼接画圆角，不依赖图片）；**浅色版**（Yaru × LIGHT）= 白卡片 + 主色压深（198,62,20）+ 状态色整体压深（亮绿/亮红/黄在白底对比不足）
  - **浅色系里 `border` 必须比 `text_dim` 更浅**：它兼作"禁用 / 未聚焦"色（页脚灭臂、未聚焦卡片底），否则"禁用"会读成"更黑更抢眼"，语义反转
  - **Custom（自定义，2026-09-13 d108/d109 落地）**：不写死色值，只存用户所选主色 HSV（config `customH/customS/customV`，h 0-359 / s 0-100 / v 0-100），运行时由 `theme_set_custom()` 经 `theme_hsv()` 推导整套（**暗 / 浅各一套**，明暗轴照常正交）：背景 = 主色压暗 + 降饱和、卡片 / 边线逐级提亮、`accent` = 主色、文字按对比度取白/深、`accent_text` 按主色感知亮度（0.2126R+0.7152G+0.0722B）取深/白；浅色系 `border` 比 `text_dim` 更浅（同"禁用=更弱"口径）
    - **色盘页（`PAGE_COLOR_PICK`）**：设置页「主色」行**仅在主题 = Custom 时显示**（其他主题下无意义；隐藏行不占位、不参与上下导航、不注册触摸），点进色盘页 = 三条 HSV 渐变条（上下选条、左右调值、触摸点 / 拖定位），**进入即以 Custom 实时预览整套配色**；确认 = 落盘主色并切到 Custom，取消 = 还原盘上主色与进入前色系
- 默认主题：Yaru 深色

### 5.5 字体

**决策（2026-09）：freetype + 内嵌开源字体，替代 PVF 作主渲染路径。** 依据：

- libvita2d 的 `vita2d_font` 即 freetype 封装（内部 `FT_Init_FreeType` + face 创建），支持从文件/内存加载任意 TTF/OTF：`vita2d_load_font_file` 走**文件 face**（`FT_New_Face`）、`vita2d_load_font_mem` 走**内存 face**（只存指针不拷贝，buffer 须常驻）——两者性能差 150~180×，见 §5.5.1
- PVF 是固件内置字体（实为 otf/ttf 改名，位于 sa0 系统分区），覆盖范围固定且不可扩：即便用 `vita2d_load_system_pvf` 按语言组合注册（拉丁 + 简体中文），生僻字/非简体字符仍会缺字，只能算零体积过渡方案
- 自带字库才能保证"对方发来任意中文名都能显示"

**实现（2026-09-04 落地；d124 起字体换 Noto Sans）：** 双字体逐段路由，均为 Google **Noto Sans**（SIL OFL 1.1，随仓库入库，见 `fonts/LICENSE-OFL.txt`）：

- `fonts/NotoSans-Regular.ttf`（拉丁）+ CJK 用 `fonts/NotoSansCJKsc/tc/jp-Regular.otf`（简 / 繁 / 日三份，各约 16.4MB，都含全部 CJK 字形），按**当前界面语言**取地区版本（`cjk_slot_current`：繁中台 / 港→tc、日→jp、其余→sc）；CMakeLists 打进 VPK `app0:/fonts/`
- 单字码点 ≤ 0xFF（ASCII / Latin-1）与**通用标点 U+2000-206F**（省略号 U+2026、弯引号、破折号…——CJK 字库缺、拉丁字库含）走拉丁字体，其余走 CJK 字体；`widgets.c` 内按字符分成连续同字体段、整段一次绘制（保留 kerning、控制调用次数）。2026-09-07 修复：早期"码点>0xFF 一律 CJK"把省略号等发给缺字形的 CJK 字库 → 中文文案省略号渲染成方框
- freetype 的 y 是**基线**、size 是像素字号；`w_text` 的 y 保持"行首升部线"语义，内部基线放在 `y + FONT_ASC*size`（CJK 满格字形顶比例，实测 glyf yMax/upem；盒 ascender 1.043 含 em 上方行距空白，基线过高会整体偏下）。字号换算 `scale=1.0 → 20px`（`FONT_PX`/`FONT_ASC` 常量集中在 `widgets.c`，整体缩放只改一处）。**换 Noto Sans 后 `FONT_ASC` 由 0.81 调至 0.88**（Noto CJK 满格字字形顶实测 0.875~0.90，见下「校准状态」）
- **性能事实 + 按字号分槽（2026-09-04 晚落地）**：libvita2d freetype 后端自带**字形级 atlas 缓存**（FTC_ImageCache + 共享 texture atlas），同一字体对象内字形只栅格化一次、后续直接 blit；但 atlas 缓存**不分字号**——同一字形先以小字号缓存、再以更大字号绘制时会把小位图整体放大（draw_scale≠1），槽位间渗色一并放大，表现为大字笔画不均、横向条纹。这是真机"大字横线/参差"的根因，故改为**按像素字号分槽**：`ui.h` 暴露 `font_get(size, cjk)`，`ui_main.c` 按字号懒加载独立字体对象（各自 atlas、draw_scale 恒为 1），对 `widgets.c` 绘制 API 透明。早期"需字符串级缓存"的顾虑依旧不成立
- 字库用纯 CJK fallback 单字体不够（无 ASCII），故拉丁/CJK 必须成对；字体本身无 GPL/许可冲突
- 缺字行为：字符所在字库无字形时，freetype 的 `.notdef` 会被栅格成空框并显示（不是"跳过不渲染"）——所以字体路由必须保证常用字符都进含其字形的字库；生僻字（两库皆缺）才会真正空白/空框

**校准状态（2026-09-04 首验；2026-09-14 换 Noto 后重标定）：** 升部按字形实测——Droid 时代 `FONT_ASC=0.81`，换 Noto Sans CJK 后满格字字形顶实测 **0.875~0.90**（16 / 20 / 26 / 34px 档分别为 0.875 / 0.900 / 0.885 / 0.882），取 **`FONT_ASC=0.88`**（盒 ascender 1.043 不用，理由见上）；字号基准 `FONT_PX=20px@scale1`，配合按字号分槽绘制后大字/小字均显示正常；若个别场景仍需微调，改 `widgets.c` 里这两个常量即可。`w_text_w` 返回行高 h=字号（近似）用于垂直居中，如需精确按字形度量再改。

**自定义字体替换/追加已销账（2026-09-07）**：内嵌双字体已覆盖实际场景，无必要开放字体自定义；若将来出现真实需求再按新里程碑评估。

#### 5.5.1 字形冷启动：定案

- **根因**：libvita2d 默认开文件 face，字体在 VPK 的 `app0:`（deflate 压缩流）里；FreeType 每取一个新字形都要包内随机读并解压，实测 ~40ms/字形（与字号无关）。
- **方案**：启动时把字体文件整份读入 RAM（UMA，无需搬显存），字体对象改走 `vita2d_load_font_mem`；随后删除开屏与全部预热逻辑。
- **结果**：`warm total` 5315ms → 65ms，开机到主界面 ≈665ms。
- **约束**：字体对象按字号分槽、CJK 按界面语言选地区版本；换语言在帧外重建字体对象；进设置页后台预读另两份 CJK，出页释放。
- 原始探针数据与 d38-d40 历史方案见 [changelog.md](changelog.md)「附录：实现细节」。

### 5.8 行几何与长文本口径（d149~d157 定稿）

**只收敛"几何参数入口"，不做样式表覆写层。** 原"样式表"方案（默认一套样式 + 调用点覆写数值 / 字号）能覆盖的只有值行那一族，两行排 / 密集行反正要自绘，多一层"默认表 + 覆写"只会让排查观感问题时多跳一层，故弃用；`RowGeom` 是输出参数，"要偏离就改取回的字段"已经买到了"一处调间距"的收益。

- **几何常量单一来源（`src/ui/ui.h`）**：页头 `HDR_H 52` / 页脚 `FOOTER_H 46`；列表可视区 `LIST_TOP 76` / `LIST_BOTTOM 492` / `LIST_VIEW_H`；行 `ROW_H 56`（可见高）/ `ROW_STRIDE 62`（步进）/ `ROW_PAD_X`、`ROW_PAD_R 24` / `ROW_GAP 12`（主文本与右端元素最小间距）；行内字号档 `SC_TITLE 1.7` / `SC_GROUP 1.05` / `SC_MAIN 1.25` / `SC_SUB 1.0` / `SC_DENSE 1.1`（像素字号 = scale × 20，见 `w_font_px`）。**收敛前同一个概念有 2~5 个取值**：列表顶 76 / 104（主页两栏）/ 68，行步进 62 / 60 / 58，左内边距 20 / 24 / 40 / 48 / 60，右锚点 5 种算法。
- **`row_geom(Rect, RowKind, int reserve_right, RowGeom *g)`（`widgets.c`）**：把行型翻译成 `x_text`（内容左锚点）/ `x_right`（右端元素右边缘）/ `w_text`（主文本可用宽，已扣 `reserve_right`）/ `y_main` / `y_sub` / `main_sc` / `sub_sc` / `row_h`；页面拿结果自己画内容。配套 `w_text_right(x_right, …)` 收掉原先 4~5 种手写右对齐。行型只有 3 档：
  - `ROW_VALUE` —— 单行主文本 + 右端（文字 / 色块 / ✕ / 勾选）：设置页、文件浏览、主页已选文件行、接收设置行；**右端是什么不改变几何**，故行尾控件不是独立行型，走 `reserve_right`。
  - `ROW_2LINE` —— 主上副下：主页设备行、设置页保存目录行。
  - `ROW_DENSE` —— 单行 + 下方附属进度条：进度页。
- **长文本三种截断口径（定死，页面按内容类别选）**：路径 / 目录字符串（保存目录、当前路径、已选文件完整路径）→ `w_text_lead`（**头部省略**，画成 `…/PSPSEND/Download`，末级目录 / 文件名才是要看的那段）；名字类（文件名 / 目录名）→ `w_text_mid`（中间省略，保住扩展名）；其余不受本端控制的文本（对端别名、提示句、平台类型）→ `w_text_clip`（尾部截断）。三者都必须给 `max_w`，**不许用裸 `w_text` 画长文本**（放不下会压到相邻内容上）。
- **不纳入本次收敛**：页头 / 页脚 / 弹窗 / 色盘页各有自己的模块；设置页的分组标题行、logo 行、适配说明行不是"行"，色盘页 HSV 条同理（常量仍在各页内）；主页两栏的 `PANE_*` 仍在 `pages_internal.h`（栏宽 / 栏间距是两栏专有，不参与 `row_geom`）。

## 8. 实现约束与注意事项

- multipart 边界解析（上传 body 格式以协议文档为准）
- 大文件流式写盘（内存红线）
- 网络异常处理：断连、超时、设备休眠、飞行模式恢复
- 内存监控调试：`mallinfo()`（newlib 堆）+ `sceKernelGetFreeMemorySize()`（系统余量）——注意统一内存下显存块（sceKernelAllocMemBlock）不计入 mallinfo，需结合查看
- 传输速度预期：**下行 5.43~5.54 / 上行 4.72~4.85MiB/s**（d181 裸 TCP 标定，见 §4.5；802.11n 单天线，上下行不对称、socket 缓冲已最优），实测接收 5.21 / 发送 4.66MiB/s，两端均已到顶。早期"10~20MB/s"的乐观估计已被实测推翻
- 发现侧的硬约束（d193）：官方 2.x **register 成功才入库**、总预算 **500ms**；本机单条 TLS 握手 ~240ms，因此**同一时刻只允许一条公告对应的握手在跑**（三份公告错峰 1s/2s）。另：曾用 ping 测得「Wi-Fi 省电模式」把 RTT 从 ~1.9ms 拉到平均 **60ms**（峰值 148ms，锯齿状），一度怀疑它影响发现；但真机端到端实测（省电开 / 关各测）**发现速度与传输吞吐均无明显差异**，故不作为影响因素——802.11 省电只在**空闲期**生效（doze 后按 DTIM/beacon 周期唤醒，beacon 通常 100ms），有持续业务时网卡保持唤醒，故空闲 ping 的 RTT 差异不代表传输期性能。该开关属系统设置，应用层也改不了
- 身份验证码口径（d195~d200）：两侧比对的是**证书指纹原文**（DER 的 SHA-256、大写 hex），组合方式为 `sort(本机指纹, 对端指纹)` 后**直接拼接**，不是哈希后的短码；因此两端必须用同一对字符串（各自"自己公告的指纹" + "对端的公告/证书指纹"），大小写与排序口径都不能各写一套。图标模式（d200）在这条串上再走一步：`SHA-256(128 hex)` 取**前 16 字节** → **base-260** 得 16 个数（长度 `ceil(32*4*log2/log260)=16`，首位只可能落在字母表前 203 项）→ 下标即图集格子号；任何一步换口径（例如多取几位摘要、改成 32 位、下标再查一次表）都会与官方图标不一致
- 图集与官方字母表绑定（d200）：图集必须按官方 `iconAlphabet` 的**名字升序**生成（260 项，顺序即下标），官方改表就要重跑 `scripts/gen-verify-icons.py`（脚本内置 260 项名字 + 码位并自检覆盖）。**不要退回"运行时用图标字体画"**：libvita2d 的字形缓存是固定 512×512 单页、永不淘汰，`atlas_add_glyph` 失败时上层直接 `continue`（溢出**静默不画**），且它的 `utf8_to_ucs2` 不认 4 字节码位（字母表里 45 个图标在 U+FFFF 以上）；图集纹理只能在启动时**帧外**创建并常驻，绘制固定 1:1 + POINT 采样
- 决定窗口的口径（d201/d202）：60s 指**确认页上无操作**，不是墙钟。UI 进设置页 / 验证页（含其中打开的目录选择页）时要 `recv_decide_hold(1)`，回确认页或有输入时 `recv_decide_hold(0)` / `recv_decide_touch()`——两者都把截止时刻重开成"现在 + 60s"。**每个 pending 结束路径都要清 hold、新 pending 起步也必须清零**：漏放一次会让下一份请求永不超时（表面像"卡住"）。剩余时间单位：`now_us()` 与 `RECV_DECIDE_TIMEOUT_US` 都是**微秒**，显示要除 1000000（d202 踩过：误按毫秒当秒，倒计时从 900:00 起跳）
- 身份验证的信任边界（同批）：入口只对 **https 对端**开放。明文连接的 fingerprint 是 JSON 自报值（官方同样把按钮画成禁用态），比对没有意义。接收侧的"对端指纹"取 **TLS 握手算出的叶证书 SHA-256**，不取 prepare JSON 里的 `fingerprint`（协议规定 HTTPS 模式下该字段被忽略）
- 接收确认页的"对方撤销"检测（d199）：官方发端在**等接受**阶段是靠**关掉 prepare 连接**表达取消（那时还没有 sessionId，`/cancel` 用不上），服务端只能在挂起期间**主动探连接**。本套 SDK 没有 `select`，用 `MSG_PEEK|MSG_DONTWAIT`：`EAGAIN` = 仍连着，FIN / `ECONNRESET` / `ENOTCONN` = 已断，TLS 的 close_notify 表现为首字节 `0x15`（alert）。**认不出的错误必须不下结论**，否则正常连接会被误判成断开、一进确认页就 403
- **已评估（暂不做）：传输前压缩**（2026-10-23，test 分支上的临时基准程序，测完即删；条件：333MHz app 模式、2MiB 语料、64KiB 独立分块、网络取上文 5.21 / 4.66MiB/s）：**只有 LZ4 值得考虑**——text 类语料压缩比 **0.53**、压缩 **13.4**MiB/s、解压 **19.8~29.6**MiB/s，端到端 `min(C, N/ratio)` ≈ **9.8**MiB/s，即 **约 1.9×**（收发两向同量级）；不可压缩数据压缩比 ~1.00（LZ4 还会膨胀 0.4%），但它的压缩速度 16~82MiB/s 远高于网络，**吞吐不变**，只多耗约 6% 单核时间。zlib 各档压缩只有 0.57~3.75MiB/s（端到端 0.14~0.72×，**比裸传更慢**），bz2 解压只有 1.5~1.9MiB/s（接收侧会被拖到 1.8MiB/s），均出局。双线程分块（mt2）实测并行加速 1.8~1.9×，但 LZ4 单线程已超过网络所需，并行无收益。**前提**：官方协议没有压缩字段，只能作为私有扩展协商启用，对官方客户端仍是裸传

## 9. 开放问题

> 已闭环问题见 [changelog.md](changelog.md)「附录：实现细节」；以下只保留仍未落地的事项。

- [ ] **传输前压缩（LZ4）：2026-10-23 评估后暂不做**——实测数据与淘汰过程见 §8：LZ4 在可压缩文件上约 1.9×（收发两向），zlib/bz2 全负。官方协议没有压缩字段，收益面只到 PSV↔PSV 与将来的自家 PC/Web 端。**触发条件**：做自家 PC/Web 引擎（Web 网页端 d208 已落地，但浏览器页不参与压缩协商），或要 PSV↔PSV 提速时再做。届时口径：LZ4 块格式（vendor 官方 `lz4.c`，约 120KB 代码、无额外堆）；64KiB 独立块，每块自带头（原始长度 + 压缩长度）；**压不小于原块就发原始块**（不可压缩数据会膨胀 0.4%，也省掉无效解压）；能力协商放在 `?apiVersion` 旁的参数上，对方不认就裸传；接收侧解压 19.8~29.6MiB/s 已够，不需要并行解压
- [ ] **指纹白名单（B）/ 接收端 PIN（C2）：2026-10-23 决定暂缓**——B 的算法只有"按 64-hex 查表"，成本全在 config 存储 + 设置页两行 + 确认页开关 + i18n + 指纹变更后的清除，而"每次都要点 Accept"目前还不是抱怨点；C2 的价值只在无人值守收件，同样依赖 Web / 常驻场景。**触发条件**：出现"无人值守也能安全收"的需求（Web 网页端 d208 已落地，但网页走 PIN + 接收确认，不构成无人值守场景）。届时的口径（对齐官方 Quick Save 的调研结论）：判定点放 **prepare 层**（握手内拒绝给不了 UI 反馈，也拿不到 IP / 清单）；指纹优先取 `Conn.peer_fp`（证书，不可伪造），**为空（明文 / 对方不出证书）永不自动放行**；**只做 Favorites 档**（对齐官方 `QuickSaveMode.paired`），不做官方 `on` 全自动档（ux0 空间有限，谁都能静默写盘，风险大于收益）；清单存 config（逗号分隔 64-hex，上限 16~32 台），并提供"清除"入口
