# PSVSend 设计文档

> 面向 PS Vita 的 LocalSend 协议（v2）兼容客户端。本文件记录前后端架构、关键决策与开发路线。

## 1. 项目目标

- 在 PSV 上实现 LocalSend v2 兼容客户端，与局域网内其他 LocalSend 设备（手机 / PC）互相收发文件
- 协议目标 **v2**（理由见 §3）：v1 已废弃；v3 的签名 / WebRTC / PIN 体系复杂，PSV 资源有限，且官方客户端同时兼容 v2/v3，v2 生态覆盖最广

### 实现现状（2026-09 ~ 2026-10）

- **已落地（发送方向）**：UDP 组播发现 / register 入表 → UI 选设备、浏览 ux0 选文件 → `transfer.c` 按对方 announce 的 protocol 走 HTTP 明文或 HTTPS（mbedTLS 3.6.5、锁定 TLS1.2）执行 `prepare-upload` / `upload`，带进度回写与本地取消。HTTPS 连接自动出示内嵌设备身份证书（mTLS，应对 2026 官方 Rust 内核接收端强制客户端证书），并按对方指纹锁定其证书（详见 §3 决策表）。**发送体读/发双缓冲流水**（d182，见 §4.3/§4.5）：读盘与加密发送各占一条线程，实测 3.53 → **4.66MiB/s**，已到裸 TCP 上行标定上限。**发送前 sha256 校验**（d185）：设置项 `sendSha` 默认开，预扫后把每文件 sha256 写进 `prepare-upload`；预扫同样是读+哈希双线程流水（实测 8.41MiB/s，串行只有 4.65），进度显示在发送等待页（按文件个数均分的分段进度条 + 当前文件 x/N）。**接收 PIN**（d178）：对端开了 receive PIN 时 prepare 回 401，发送线程挂起等 UI 用系统键盘输入，带 `?pin=` 重发（最多 3 次，再 401 提示 PIN 错误；429 提示对端忙）。
- **已落地（接收方向）**：对方 prepare-upload → 自动弹接收确认页（Accept / Setup 逐文件勾选 / Reject）→ upload 由 http.c 提供流读回调、receive.c 边收边写 `ux0:data/psvsend/downloads/`（先 `.psvsend.tmp` 收完改名，sha256 校验，断流/校验失败删残留，开机清扫遗留）。sha256 校验由设置项 `recvSha` 控制（d186，默认开）：开启时与写盘/解密三级并行、实测零墙钟成本；关闭后不比对也不起校验线程（用途是对端哈希实现有误时不被 422 拒收）。兼容对方无 Content-Length 的 **chunked 流式上传**（http.c 内嵌解码状态机）；同一会话内多文件由对方**并发**发起 upload，接收侧按文件独立流式收体（每文件各自 busy 状态，互不阻塞；d68 修复了 v2.1.0 起后到文件被 409 拒绝的缺陷）。取消/放弃/空闲超时等状态经快照接口给 UI 展示结束原因。**单文件失败不终止会话**（d188，与官方一致）：写盘失败 / sha256 不符 / rename 失败 / 无法创建文件等只标记该文件，其余文件继续收；全部收尾后若有失败，会话终态为 `RECV_ST_PARTIAL`（进度页 `Complete, N failed` + 警示色）。断流 / 用户取消 / 空闲超时仍是会话级（对端已不可达）。announce 已声明 `download:true`。sessionId 与每文件 token 由 `getentropy` 生成（失败回退时间种子，d178）。
- **已落地（传输上下文生命周期，d190）**：收尾不再"等 join 成功再释放"——接收 8 个 / 发送 6 个**静态槽位**（FREE / ACTIVE / ZOMBIE）持有线程句柄与上下文，缓冲进 ACTIVE 才分配；等不到线程退出时**遗弃整条流水线**（不 `DeleteThread` / 不 free 缓冲 / 不关 fd / 不删 `.psvpart`）转 ZOMBIE，线程真退出后由 `reap_zombies()`（`sceKernelGetThreadExitStatus`）回收。`cleanup_parts` 跳过 orphan、`alloc_paths` 避让 ZOMBIE 路径，槽位满回 503；发送侧 join 超时的文件按"无 sha / 发送失败"收尾。修掉审查 P1-4 的 UAF（写盘阻塞超 10s 后线程访问已释放内存），并用临时故障注入版（构建号 d191，验证后已删、未提交；写盘强制卡 30s）真机验证遗弃 → 回收 → 槽位复用路径。
- **已落地（接收方向 TLS 化，d173~d180）**：http.c 服务器改为**单端口双栈**——worker 先 `sceNetRecv(fd,p,1,0)` 嗅探首字节，`0x16`（TLS handshake record）走 mbedTLS 服务端握手，否则按明文 HTTP 解析（嗅探字节缓存在 `Conn.p`，不丢包）。服务端出示同一张设备身份证书，announce / self_info / prepare 三处统一声明 `protocol:https` + 该证书指纹；TLS 锁 1.2，密码套件优先 **ChaCha20-Poly1305**（Cortex-A9 无 AES/SHA 硬件指令，AES-GCM 实测慢约 20%），再回退 AES-128/256-GCM。信任 **trust-first**：`VERIFY_OPTIONAL` + 空 CA 占位，`srv_verify` 只记对端指纹、`*flags = 0`（不拒绝），**不防主动 MITM**，白名单 / 验证码后置（§9）。**握手去关键路径**（d175）：设备身份（解析证书 + RSA CRT）改为全局解析一次并在启动预热，握手内不写 dlog（dlog 是同步写 ux0，每次几十毫秒）——握手 447~521ms → **230~250ms**，稳定进官方 register 请求的 500ms 总预算，官方客户端重新能主动发现 / 扫描到 PSV。**数据面分线程**（d177，见 §4.3）：收体解密与写盘 / sha256 校验重叠，实测 2.81 → **3.60MiB/s**。**三级流水**（d180）：解密 / sha256 / 写盘各占一条线程、3×64KB 轮转缓冲，sha 与写盘处理不同块真正重叠，实测 **5.21MiB/s**（148.6MB / 27.2s），瓶颈已转移到 socket 收 + TLS 解密本身（等价 ~5.58MiB/s），ux0 写与 SHA-256 都不再是上限。
- **已落地（发现补充）**：Vita 收不了 UDP 组播、也绑不了 53317，设备表主要靠对方主动 register 与 `scan.c` 主动扫描（向 /24 各 IP 的 53317 POST register 拿 member info）。扫描按 **TLS→明文顺序**探测并携带设备身份证书（2026 官方 Rust 内核接收端强制 mTLS 客户端证书），明文兜底兼容纯 HTTP 端；**优先探测历史在线设备**（config `knownIps` 持久化、LRU、上限 24，入表即记录），常用设备实测轮次开始 ~0.7s 内出现。曾修复两处致手动扫描失效的 bug：`s_read_resp` 未把响应 body 移到缓冲区头部（JSON 解析永远失败、found 恒 0）；TLS 探测静默失败。UI 三角键手动触发。
- **已落地（发现稳定性，d193）**：官方 LocalSend 2.x（Rust 内核）的发现口径是"**register 成功才入库**"——收到一份公告就回一次 `POST /register`，**总预算 500ms**（`DEFAULT_DISCOVERY_TIMEOUT`），成功才把设备登记进列表；而 PC 端的"扫描"只是发自己的公告等对方回 register，PSV 收不了组播、无法回扫，**只能靠自身公告让对端反过来探测自己**。此前每轮**同时**发三份公告（组播 / 受限广播 / 定向广播）：定向广播地址修对之后（P1-5 曾混入 d190 构建、随后按要求剥离），第三份才真正送达对端，于是对端对每份各开一条连接 → 三条 TLS 握手并发抢 CPU，单条从 240ms 拖到 **405~513ms**，两条被对端在 500ms 掐掉，设备在对方列表里时有时无（真机实测每轮 3 条连接、1 成 2 败）。现改为**错峰发送**：组播立即、受限广播 +1s、定向广播 +2s（tick 粒度 500ms），实测单条握手回到 **226~234ms**、每轮 3 次 register 全成功，官方客户端"秒扫出"。同批修正定向广播地址：`ip4` 是网络序字节躺在内存里，按 uint32 位运算会算出 `255.b.c.d`，改为直接改内存第 4 字节得到 `a.b.c.255`（此前该包发不出去，等于少一条兜底）。
- **已落地（代码审查第二轮 P2 清理，d194）**：第二轮审查剩余的低概率 / 代码卫生项一次清完，正常路径行为不变。① `http.c`：本机身份解析锁改由 `http_start` 预建（与连接登记表锁同处），`own_identity()` 只做锁内二次检查，修掉两条连接并发首进入时"各建一把锁、各锁各的"导致并发 init/parse 全局证书上下文；② `http.c`：端口候选表删掉末位 `0`（`bind(0)` 必成功但实际端口不可知 → 公告带端口 0、`g_port == 0` 让重入判断与 watch 重启条件同时失灵），全候选失败改为返回失败交 watch 重试；③ 接收进度页的错误文案不再指向块内 `RecvStatus` 快照（拷进函数级缓冲，消除 UB）；④ `transfer.c` / `scan.c` 检查 `sceKernelStartThread` 返回值：transfer 起不来会留下 `active=true`（之后所有发送被拒）+ 线程对象泄漏，现删线程并清状态；scan 补删线程对象；⑤ 速度采样新增 `spd_reset()`，由 `start_send` / `start_recv` 在会话起点复位（两笔间隔 <1s 时 `spd_update` 的">1s 没画就作废"判据不成立，会沿用上一笔样本）；⑥ `config.c` 直写兜底短写时删掉半截 config、保留完整 tmp 交给 `config_init` 自愈（自愈要求"config 缺失 + tmp 完整"），写全才删 tmp。真机回归：端口 4567、三份公告错峰正常、双向传输 0 失败、设置重启后仍在。
- **已落地（稳定性，v2.0.0）**：修复待机唤醒 / Wi-Fi 断开恢复后卡「网络未就绪 / 没扫到设备」——watch 看门狗单线程低频轮询 netctl + 全互斥 `initCount=0` 语义修正（发现/扫描/收发/net 各互斥均改为无人先持锁），恢复后 UI 心跳自动续上；另曾用 6s 模拟断网窗口复现，现该调试开关已置 0（net.c `PSVSEND_SIM_DOWN_MS`，需要时 cmake 覆盖）。
- **已落地（渲染稳定，v2.0.0）**：修复偶发 **GPU render crash**（先兆为界面「三角形空白撕裂」→ 系统判 render gpu crash 重启）。根因：主循环缺 `vita2d_wait_rendering_done()`，每帧 swap 后 GPU 队列无收敛点，渲染/显示队列超前回绕导致撕裂与驱动状态错乱；修复：每帧 swap 后等待渲染完成（ui_main.c）。字体对象另改为启动帧外预载（`font_preload_all`），堵住"渲染中途创建 GPU 纹理"的隐患（非本次根因，作加固保留；d122 起字体改从内存建，预载仍保留）。
- **已落地（字体，d120-d126，见 §5.5）**：**字形冷启动根治**——定位到 libvita2d 的 `vita2d_load_font_file` 开的是**文件 face**，字体放在 VPK 的 `app0:`（deflate 压缩流）里，FreeType 每取一个**新字形**轮廓都要包内随机读一块并解压，实测 **~40ms/字形**（同字同号对照：文件 face 43.5ms vs 内存 face 0.19ms，差 150~180×；且与字号无关，故"砍字号档位"无效）。改为启动一次性把字体文件读进 RAM（UMA 架构，无需搬显存），字体对象走 `vita2d_load_font_mem`——`warm total` 5315ms → **65ms**（81×），开机到主界面总开销 ≈665ms。此后**删掉开屏画面与 `pages_warm_all()` 全部预热逻辑**（预热已无意义），`ui_run` 直接建齐字号字体对象。**字体换 Noto Sans**：拉丁 `NotoSans-Regular.ttf` + CJK 按界面语言取地区版本 `NotoSansCJKsc/tc/jp-Regular.otf`（简/繁/日，各约 16.4MB，都含全部 CJK 字形，差别只在同一码位默认取哪个地区的字形），`FONT_ASC` 由 0.81（Droid 标定）调至 0.88（Noto CJK 实测）；换语言时在每帧 `start_drawing` 之前帧外重建 CJK 字体对象（`vita2d_load_font_mem` 会建显存纹理，落在渲染 pass 中途有 GPU crash 风险），首次切到某地区读盘 ~1.6s 后该地区字体常驻 RAM。字体随仓库入库（SIL OFL 1.1）。

## 3. 关键决策

| 决策 | 结论 | 理由 |
|------|------|------|
| 协议版本 | **v2** | v1 废弃；v3 复杂（nonce 签名 / WebRTC），官方保持 v2 向后兼容，生态主流是 v2 |
| 传输 | HTTP 明文与 HTTPS 双支持，按对端 announce 的 protocol 自动选择 | 明文互通无碍；对端为 https 时必须加密 |
| TLS 方案 | **mbedtls**（工具链自带 3.6.5），锁定 TLS1.2 | PSV 系统 SceSsl 对 homebrew 不可用；TLS1.3 的证书校验不走 per-cert 回调，指纹 pin 依赖 1.2 |
| HTTPS 信任模型 | 对端证书按 announce 指纹 SHA-256 **pin**（VERIFY_OPTIONAL + 自管校验回调），不依赖 CA 链 | LAN 内无公开 PKI；协议本身即以 fingerprint 标识设备 |
| mTLS 客户端身份 | 内置自签 RSA-2048 设备证书（`identity.c` + `id_cert.inc` / `id_key.inc`），对端强制客户端证书时自动出示 | 2026 官方 Rust 内核接收端对非浏览器发送方强制客户端证书，无证书即 `certificate_required` 握手失败 |
| 接收方向 TLS | **单端口双栈**：worker 读首字节，`0x16` 走 mbedTLS 服务端握手，其余按明文 HTTP；服务端出示同一张设备身份证书，TLS 锁 1.2、ChaCha20-Poly1305 优先 | 对方按 announce 的 protocol / port / fingerprint 直连，端口不能变；明文兜底是 Web / download API 的协议要求 |
| 服务端信任模型 | `VERIFY_OPTIONAL` + 空 CA，`srv_verify` 只记录对端证书指纹、不拒绝（trust-first） | LAN 无公开 PKI，先保证"加密防被动嗅探"；白名单 / 验证码后置（§9） |
| HTTP/1.1 范围 | **子集**：POST、Content-Length、**chunked 解码**、query string；响应后关闭连接 | 目标是"兼容 LocalSend"，非"完备 HTTP"。chunked 必须支持（官方 Dart 客户端可能使用）；**不支持 multipart 编码**（v2 多文件逐 POST 单文件裸流，见 §9）；解析器独立模块、防御式实现（全部读取设上限、不支持格式优雅拒绝 400） |
| 内存约束 | 按 **256MB** 设计基准（实际预算 365MB 封顶） | 512MB 为**统一内存**（CPU/GPU 共享），系统保留约 147MB，应用可拿最大 365MB（工具箱可调 256/285/333/365） |
| 文件处理 | **大文件永不整读入内存**，一律流式（收：边收边写盘；发：边读边发） | 内存红线 |
| 传输分块 | 16~64KB 缓冲 | PSV socket / sceIoRead 的大块缓冲限制 |
| 应用数据目录 | `ux0:data/psvsend/`（含 `downloads/` 接收目录），首次启动 `sceIoMkdir` 幂等创建 | 符合 PSV 惯例，homebrew 有写权限 |

### 4.2 核心数据结构

```c
// 设备表（发现线程维护，mutex 保护）
typedef struct {
    char ip[16]; int port;
    char alias[64], fingerprint[64], protocol[8]; // http/https
    uint32_t last_seen;      // 超时未更新移除（如 60s）
} Device;

// 会话（收发共用一套结构）
typedef struct {
    int  id;                 // sessionId
    int  direction;          // INCOMING(收) / OUTGOING(发)
    char peer_ip[16];
    FileEntry files[];       // 每文件: fileId、token、name、size、已收字节、状态
    int  state;              // AWAIT_CONFIRM → TRANSFERRING → DONE / CANCELLED
} Session;
```

### 4.3 线程模型

| 线程 | 职责 |
|------|------|
| UI 主线程 | 渲染 + 消费事件队列刷新界面 |
| 发现线程 | UDP recvfrom 循环 + 定时发 announce |
| HTTP 服务器线程 | accept 循环，**每连接一个工作线程**（LocalSend 并行传多文件）；工作线程内先做 **TLS / 明文嗅探**（首字节 `0x16`），TLS 连接现场做服务端握手 |
| 收体流水线线程（recv） | 每个 upload 起两条（对端给了 sha256 且设置项 `recvSha` 开时）或一条：生产者只做解密 / 攒块，**sha 线程**只算校验和，**写盘线程**只 `sceIoWrite`；3×64KB 轮转缓冲 + `sem_free`/`sem_sha`/`sem_job` 计数信号量，块逐级传递、sha 与写盘处理不同块（d180，三级流水） |
| 发送线程（xfer） | `prepare-upload` 一条连接等对方决定；接受后起 N 个 worker 线程并发上传（N = config `maxParallel`，上限 6），join 完全部 worker 后**统一写一次终态**（见 §1「实现现状」）。每个文件另起一条**读盘线程**，worker 本线程只做 `mbedtls_ssl_write`：2×32KB 轮转缓冲 + `sem_free`/`sem_full` 计数信号量，读满声明 size（或读失败）投 `len=0` 终止块（d182，读/发双缓冲流水） |
| 预扫线程（xfer，d185） | `prepare-upload` 之前按文件顺序算 sha256（设置项 `sendSha` 默认开）：一条读盘线程 + xfer 线程自身做 `mbedtls_sha256_update`，缓冲结构与发送侧同一套（2×32KB 轮转）。每条线程各自跑满（读 9.7 / 哈希 8.8MiB/s），合流实测 8.41MiB/s |
| 定时器（可并入发现线程） | 设备超时清理、announce 周期触发 |

共享数据（设备表、会话表）统一 mutex 保护。

### 4.5 HTTP 服务器要点

- 路由：`/api/localsend/v2/register`、`prepare-upload`、`upload`、`cancel`、`info`
- `prepare-upload` → 生成 sessionId，为每文件分配 fileId + token，返回 `{sessionId, files:[{id, token, fileName, size}]}`；同时向 UI 抛"待确认"事件
- `upload?sessionId&fileId&token` → 校验会话与 token 匹配 → 流式写盘（先临时名，完成后重命名；同名加序号避免覆盖）
- 安全底线：只收"prepare 过"的 fileId+token，否则 400；拒绝时回 401/403
- **单端口双栈**：工作线程先 `sceNetRecv(fd,p,1,0)` 读首字节，`0x16` → mbedTLS 服务端握手（失败即关连接），否则把该字节塞回 `Conn.p` 按明文 HTTP 解析（`conn_read` 先吐缓存，不丢包）。端口候选与 announce 不变，`protocol` 改声明 `https`
- **服务端身份与信任**：出示 per-device 自签 RSA-2048 设备证书（§3），`VERIFY_OPTIONAL` + 空 CA；`srv_verify` 只把对端证书 SHA-256 记到 `Conn.peer_fp`，不中断握手（trust-first，白名单 / 验证码的判定点就留在这里）。身份解析全局缓存一次 + 启动预热，**握手路径内不写 dlog**（同步写盘几十毫秒，会挤爆官方 register 的 500ms 预算）
- **吞吐**：收体走三级流水（解密 / sha256 / 写盘各一条线程，§4.3），实测 **5.21MiB/s**（148.6MB / 27.2s）；瓶颈是 socket 收 + TLS 解密本身（等价 ~5.58MiB/s）。发送方向走读/发双缓冲流水（d182，§4.3），实测 **4.66MiB/s**（148.6MB / 30.4s，发送体 28.8s = 4.92MiB/s），已达**裸 TCP 上行标定上限**（d181 专项测试：上行 4.72~4.85、下行 5.43~5.54MiB/s，socket 缓冲已最优、调大反而更慢）。两端都到顶，详见 TODO「性能」的标定数据
- 接收文件写入运行时保存目录（默认 `ux0:data/psvsend/downloads/`，UI 可选：config `saveDir` 持久 / 接收 Setup `recv_dir` 仅本次，见 §1「实现现状」）

### 4.6 HTTP 客户端要点

- 流程：register（可选）→ `prepare-upload` 拿 session（只有这一条连接）→ N 个 worker 并发 `POST upload`（协议 §4.2 明示 `This route can be called in parallel.`）→ cancel 清理
- 按**接收端 announce 的 protocol / port 字段**决定 http/https 与端口——明文即可互通
- 上传：32KB 分块，**读盘与加密发送各一条线程**（2×32KB 轮转 + 信号量，d182）；发送窗口没空时先让出 CPU 8 轮、再退避 1ms（原文 20ms，约四成块会撞一次）。**每个文件一条连接**，故每文件各做一次 TLS 握手（N 并在途，握手也并行）
- **发送前校验**（d185）：设置项 `sendSha` 默认开时，`prepare-upload` 之前先按文件顺序预扫 sha256（读+哈希双线程，8.41MiB/s ≈ 12s/100MB），结果逐文件写入请求的 `sha256` 字段；关闭则字段为 `null`，与旧版行为一致。预扫进度显示在发送等待页（按文件数均分的分段进度条 + x/N），可按 ○ 取消（此时 prepare 尚未发出）
- **接收 PIN（d178）**：`prepare-upload` 回 401 表示对端开了 receive PIN——发送线程置 `pin_need` 并挂起（≤120s），由 `pages_tick` 弹系统键盘，输入后带 `?pin=`（RFC3986 百分号编码）重发，最多 3 次；再 401 报「PIN 错误」，429 报「对端忙」。PIN 只在本次发送线程内保存，不落盘
- 失败分级：HTTP 4xx/5xx / 无 token / 读文件失败 = 单文件失败（其余继续）；连不上 / 握手失败 / 断流 / 等不到回执 = 连接级失败 → **全局中止**（详见 §1「实现现状」）

### 4.7 实现顺序与验证

1. `net.c` 网络初始化（跑通不崩）
2. `discovery.c` 发现 + 设备表 → **PSV 上能看到手机/电脑设备**
3. `http_server.c` prepare-upload + upload 收文件 → **电脑 curl 模拟 LocalSend 对测**
4. `session.c` 状态机 + 确认/取消
5. `http_client.c` 发送 → **官方 LocalSend App 真机对测**

### 5.2 架构：事件驱动 + 状态机

```
主循环（每帧）:
  poll 输入（按键/触摸） → 处理当前页交互
  → 消费后端事件队列（设备变更/收件请求/进度）
  → 渲染当前页 → 帧同步
```

- 后端回调**只塞事件队列**（EV_DEVICES_CHANGED / EV_INCOMING_REQUEST / EV_PROGRESS），主循环消费，线程安全不卡渲染
- 页面为状态机：`enum Page` + 每页自己的选择状态

### 5.3 双输入：按键 + 触摸统一模型

- **输入抽象层**：页面只处理抽象动作 `UiAction`（CONFIRM / CANCEL / UP / DOWN / LEFT / RIGHT / BACK / MENU），不判断物理键
- **按键路径**：十字键移动焦点，确认键触发焦点控件
- **触摸路径**：坐标命中检测 → 触发控件动作
- **控件统一**：`{ Rect bounds; UiAction action; void *target; }`，两种输入源最终走同一 action；可混用
- **确认键布局可配置**：美式（X=确认，默认，港版/国行习惯）与日式（O=确认），存 config；触摸不受影响。切换入口是该行自己的**选项面板**（d145/d146）——确认键只负责"开面板 / 应用"、不参与选档，故"用确认键改确认键"的自指负担自然消失（早期为此单开左右方向键，已废）
- **设置页值行 = 右侧选项面板（d145/d146）**：值行点整行（焦点行按确认同理）→ 右侧滑出 320px 面板（列表行宽 912→576、150ms 动画，面板态隐藏滚动条），↑↓ 选档（到顶 / 到底把那一臂画灰，**不循环**）、确认 = 应用并落盘（**面板不收起**，便于连试几档）、✗ 或点面板外 = 关且不应用；面板态拖动滚动冻结、列表焦点不动、其余按键吞掉。2 档同样走面板（交互统一）；动作行不适用（点了直接执行）；OLED 下「外观」行无档位、页脚确认段画灰。页脚文案与实现见 §1「实现现状」
- **页脚提示条独立成模块（`src/ui/hintbar.c/.h`，d106）**：页面只声明"本页用到哪些键、文案、状态"（`HintSeg` 数组），**不关心顺序**；排序、图标选择、排版只在 hintbar 内实现一处，加新按键只需补 `HintKey` 枚举与 `icon_of` / `rank_of` 两张表，各页面零改动。段结构：`key`（+ 可选 `key2` = "两个键同一动作"，画成「键 `/` 键 文案」，两个键都画出、动作文案只写一次）、`text`、`dim`（动作当前不可用 → 灰字灰图标）、`varies`、`dir_off`。**图标由键推出**（`icon_of`：`HKEY_CONFIRM` / `HKEY_BACK` 按当前键位布局在 ○ / ✗ 间取），页面不写图标，消除"键与图标对不上"的非法组合。**可选蓄力环（d159~d165）**：页面在 `w_page_footer_segs()` 之前调 `w_page_footer_charge(key, pct)`，给该键所在段的图标外画一圈进度环（pct 0~1，0 = 不画），绘制后自动清除（与 `w_clear/w_add` 同模式）——`HintSeg` 不增加动画字段，不给全仓共享结构塞一次性渲染参数
- **排序规则（hintbar 内强制，d106/d107）**：默认键序 `SELECT、START、方向键（、…）、○、✗、□、△`——先按它排本页**存在**的键，再按**不可变靠左、可变靠右**微调。"可变"（`HintSeg.varies`）只指**动作随焦点 / 运行状态改变**的段（主页 `Send↔Remove` / `Scan↔Hold to clear all`、进度页 `Cancel↔Done`、文件页 `Select all↔Deselect all`），这类整段右移；✗ 的 `Up/Back` 只是文案随层级换词、动作恒定 → 不算可变，仍按默认序排在 □ 之前。**合并段取两键中靠前的排序位定位，段内两个图标也按同一键序排列**（`seg_rank` / 段内按 rank 交换）——内部图标顺序与整段位置都不随键位布局左右跳。○ / ✗ 两项**按图标符号**定位（○ 恒在 ✗ 前），直接后果：**美式布局下"返回(○)"排在"确认(✗)"之前**，日式布局与旧版相同
- **提示条口径**：① 确认键段文案**跟随当前焦点动作**，不写死（接收确认页固定写 "Accept" 会在焦点移到 Reject / Setup 时撒谎）；② 固定不变的提示靠左、随焦点 / 状态变化的靠右；③ `HKEY_NONE` 必须为 0、`dir_off`（`HDIR_*` 位掩码，**0 = 四向全亮**）也以 0 为全亮——全仓按 `= { 0 }` 零初始化，反例会让未改动的页面凭空多出图标或灰臂
- **十字键提示 = 方向可用性指示**：`HintSeg.dir_off` 是"当前按不动的方向"位掩码（0 = 全亮），列表滚到顶/到底时对应方向变灰，用户一眼可知"这个方向按了没用"；灭臂判断**复用各页既有的移动逻辑**（如设置页 `slot_step(sl,-1)==sl` 即"上按不动"），不另写边界判断，保证提示与实际行为一致
- **触摸路径补齐（d166~d170）**：**定位 = 按键为主路径、触摸为辅助**——触摸只承诺"**不卡死 + 顺手**"，**不追求全操作对等**。据此**明确否决**两件事：① 把页脚提示条（hintbar）改成可点——它是纯展示层，改可点要吐每段 `Rect` 热区、再定义"哪段可点 / 长按怎么办"，且页脚位于**握持区**、上面恰有 Cancel / Reject / 清空已选这类破坏性动作、单段目标过小；② 启用**背面触摸板**（误触多、看不见手指位置、无视觉反馈）。本次修掉两处**触摸死锁**（"必经之路被堵"，属缺陷不属取舍）：进设置页只有 `SELECT`（全应用唯一入口）、无设备时不能扫描（设备栏 △ 短按独有，此时页面上无任何可点之物）。落地：① 主页页头右上角「扫描」（扫描进行中画灰且**不注册热区**）+「设置」两个按钮；② 设置 / 色盘 / 接收设置 / 目录选择四页页头右上角「返回」，动作**沿用各页 ✗/方块键既有语义**（`settings_leave` / `cp_cancel` / `rs_leave` / `dpick_exit`），不自创；③ 文件与目录两个浏览页**首行固定 `..`** 上级项（`..` 是路径语法里的"上级目录"；在 `files_load` 插入一处，两页共用 `g_app.files[]` 零改动获得回上级能力，光标默认落 `..` 之后第一项；空目录时页脚「选择 / 打开 / 全选」按**真实条目数**画灰——`..` 不计入内容）；④ 目录选择页 / 色盘页右下角主按钮「存到此处 / 保存」——**必须画在页脚之后**（页脚整条铺不透明背景，先画会被整块盖住）。共享组件 `w_hdr_button(cx, id, kind, dim)`：40px 方框 + 居中图标 + 52×52 热区（顶满页头高），`dim` 时画灰且不注册热区；返回箭头图标 `w_icon_back`（尖头两臂 + 横杆，避免空尖头被读成小于号）。触摸热区 id 分区：页头按钮 `0x82xx`、浏览页右下主按钮 `0x90xx`（`WID_FILES_DONE` / `WID_DIRPICK_SAVE` / `WID_CP_SAVE`）。**页脚提示条保持纯展示**、不注册热区。**明确不处理（"能绕但繁琐"，非死锁）**：文件栏「按住清空已选」（可逐行点 ✕）、文件选择页「全选 / 取消全选」（可逐行勾）、目录选择页 `□ Exit`（可 ✗ 逐层退）。**已知语义割裂**（将来若改走"当触屏应用做"再一并处理）：触摸点文件栏**不切焦点** → 页脚仍显示设备栏提示；主页点设备行**直接发送**、点文件行只移动选中（与按键"选中 + 确认"两套语义并存）

### 5.4 主题系统（theme.c）

- 主题 = 一组颜色常量（bg / card / accent / accent_text / text / text_dim / border / success / danger / warn / overlay），UI 绘制只引用主题变量（**UI 层零硬编码颜色**），**运行时可切换，下帧生效**
- 内置主题在**两个正交轴**上组合：色系（`ThemeId`：Yaru / OLED / Custom）× 明暗（`THEME_DARK` / `THEME_LIGHT`），色值表 `themes[色系][明暗]`，`theme_set(id, mode)`；config 存 `theme`（色系）+ `lightMode`（明暗），设置页对应「主题」「外观」两行。自定义即色系列加一项（Custom），明暗自动正交
  - **OLED**：纯黑 `#000000` 底 + 卡片 `#111111` + 白字高对比（PSV1000 OLED 最佳）；定位纯黑高对比，**无浅色变体**（`theme_set` 对它恒定走深色档，设置页「外观」行显示"深色（固定）"且不可改）
  - **Yaru**：深灰底 + Ubuntu 橙 `#E95420` 主色 + 圆角扁平卡片（vita2d 矩形拼接画圆角，不依赖图片）；**浅色版**（Yaru × LIGHT）= 白卡片 + 主色压深（198,62,20）+ 状态色整体压深（亮绿/亮红/黄在白底对比不足）
  - **浅色系里 `border` 必须比 `text_dim` 更浅**：它兼作"禁用 / 未聚焦"色（页脚灭臂、未聚焦卡片底），否则"禁用"会读成"更黑更抢眼"，语义反转
  - **Custom（自定义，2026-09-13 d108/d109 落地）**：不写死色值，只存用户所选主色 HSV（config `customH/customS/customV`，h 0-359 / s 0-100 / v 0-100），运行时由 `theme_set_custom()` 经 `theme_hsv()` 推导整套（**暗 / 浅各一套**，明暗轴照常正交）：背景 = 主色压暗 + 降饱和、卡片 / 边线逐级提亮、`accent` = 主色、文字按对比度取白/深、`accent_text` 按主色感知亮度（0.2126R+0.7152G+0.0722B）取深/白；浅色系 `border` 比 `text_dim` 更浅（同"禁用=更弱"口径）
    - **色盘页（`PAGE_COLOR_PICK`）**：设置页「主色」行**仅在主题 = Custom 时显示**（其他主题下无意义；隐藏行不占位、不参与上下导航、不注册触摸），点进色盘页 = 三条 HSV 渐变条（上下选条、左右调值、触摸点 / 拖定位），**进入即以 Custom 实时预览整套配色**；确认 = 落盘主色并切到 Custom，取消 = 还原盘上主色与进入前色系
- 默认主题：Yaru 深色

### 5.5 字体

**决策（2026-09）：freetype + 内嵌开源字体，替代 PVF 作主渲染路径。** 依据：

- libvita2d 的 `vita2d_font` 即 freetype 封装（内部 `FT_Init_FreeType` + face 创建），支持从文件/内存加载任意 TTF/OTF：`vita2d_load_font_file` 走**文件 face**（`FT_New_Face`）、`vita2d_load_font_mem` 走**内存 face**（只存指针不拷贝，buffer 须常驻）——两者性能差 150~180×，见 §5.5.1
- PVF 是固件内置字体（实为 otf/ttf 改名，位于 sa0 系统分区），覆盖范围固定且不可扩：即便用 `vita2d_load_system_pvf` 按语言组合注册（拉丁 + 简体中文），生僻字/非简体字符仍会缺字，只能算零体积过渡方案
- 自带字库才能保证"对方发来任意中文名都能显示"

**实现（2026-09-04 落地；d124 起字体换 Noto Sans）：** 双字体逐段路由，均为 Google **Noto Sans**（SIL OFL 1.1，随仓库入库，见 `fonts/LICENSE-OFL.txt`）：

- `fonts/NotoSans-Regular.ttf`（拉丁）+ CJK 用 `fonts/NotoSansCJKsc/tc/jp-Regular.otf`（简 / 繁 / 日三份，各约 16.4MB，都含全部 CJK 字形），按**当前界面语言**取地区版本（`cjk_slot_current`：繁中台 / 港→tc、日→jp、其余→sc）；CMakeLists 打进 VPK `app0:/fonts/`
- 单字码点 ≤ 0xFF（ASCII / Latin-1）与**通用标点 U+2000-206F**（省略号 U+2026、弯引号、破折号…——CJK 字库缺、拉丁字库含）走拉丁字体，其余走 CJK 字体；`widgets.c` 内按字符分成连续同字体段、整段一次绘制（保留 kerning、控制调用次数）。2026-09-07 修复：早期"码点>0xFF 一律 CJK"把省略号等发给缺字形的 CJK 字库 → 中文文案省略号渲染成方框
- freetype 的 y 是**基线**、size 是像素字号；`w_text` 的 y 保持"行首升部线"语义，内部基线放在 `y + FONT_ASC*size`（CJK 满格字形顶比例，实测 glyf yMax/upem；盒 ascender 1.043 含 em 上方行距空白，基线过高会整体偏下）。字号换算 `scale=1.0 → 20px`（`FONT_PX`/`FONT_ASC` 常量集中在 `widgets.c`，整体缩放只改一处）。**换 Noto Sans 后 `FONT_ASC` 由 0.81 调至 0.88**（Noto CJK 满格字字形顶实测 0.875~0.90，见下「校准状态」）
- **性能事实 + 按字号分槽（2026-09-04 晚落地）**：libvita2d freetype 后端自带**字形级 atlas 缓存**（FTC_ImageCache + 共享 texture atlas），同一字体对象内字形只栅格化一次、后续直接 blit；但 atlas 缓存**不分字号**——同一字形先以小字号缓存、再以更大字号绘制时会把小位图整体放大（draw_scale≠1），槽位间渗色一并放大，表现为大字笔画不均、横向条纹。这是真机"大字横线/参差"的根因，故改为**按像素字号分槽**：`ui.h` 暴露 `font_get(size, cjk)`，`ui_main.c` 按字号懒加载独立字体对象（各自 atlas、draw_scale 恒为 1），对 `widgets.c` 绘制 API 透明。早期"需字符串级缓存"的顾虑依旧不成立
- 字库用纯 CJK fallback 单字体不够（无 ASCII），故拉丁/CJK 必须成对；字体本身无 GPL/许可冲突
- 缺字行为：字符所在字库无字形时，freetype 的 `.notdef` 会被栅格成空框并显示（不是"跳过不渲染"）——所以字体路由必须保证常用字符都进含其字形的字库；生僻字（两库皆缺）才会真正空白/空框

**校准状态（2026-09-04 首验；2026-09-14 换 Noto 后重标定）：** 升部按字形实测——Droid 时代 `FONT_ASC=0.81`，换 Noto Sans CJK 后满格字字形顶实测 **0.875~0.90**（16 / 20 / 26 / 34px 档分别为 0.875 / 0.900 / 0.885 / 0.882），取 **`FONT_ASC=0.88`**（盒 ascender 1.043 不用，理由见上）；字号基准 `FONT_PX=20px@scale1`，配合按字号分槽绘制后大字/小字均显示正常；若个别场景仍需微调，改 `widgets.c` 里这两个常量即可。`w_text_w` 返回行高 h=字号（近似）用于垂直居中，如需精确按字形度量再改。

**自定义字体替换/追加已销账（2026-09-07）**：内嵌双字体已覆盖实际场景，无必要开放字体自定义（理由见 docs/TODO.md 闭环留痕）；若将来出现真实需求再按新里程碑评估。

#### 5.5.1 字形冷启动：根因与根治（2026-09-14 d120-d126 定案，取代 d38-d40 预热方案）

**现象**：首次切到某页 / 滚动出新行时卡顿——单字形现烤成本 CJK ≈20~32ms、拉丁 ≈2~6ms；同一字形缓存后重绘几乎免费（≈5µs/字）。d38-d40 曾以"开机预热高频页字形"规避：收窄到设备列表 / 文件浏览 / 设置顶+About（≈4.3s），期间停在 **LiveArea 壁纸开屏**、字形画进隐帧但**绝不 swap**（若 swap，display 会读到 GPU 还在异步回放的缓冲，表现为"开屏后一堆页面闪过"）；全静态页面预热（d37，6 页全烤 6226ms、屏幕全黑）与逐帧时间预算预热（d33/d34，掉帧）均因代价过高被否决。

**真因（d121 探针坐实，推翻"libvita2d 内部冷插入慢"的旧推论）**：libvita2d 默认用 `vita2d_load_font_file` 开的是**文件 face**（`FT_New_Face("app0:/fonts/*.ttf")`），而字体放在 VPK 的 `app0:`——**deflate 压缩文件系统**；FreeType 每取一个**新**字形轮廓都要在包内随机读一块并解压，实测 **~40ms/字形**（同字同号对照：文件 face 43.5ms vs 内存 face 0.19ms，差 150~180×；且**与字号无关**，故"砍字号档位"无效）。libvita2d 的 atlas / FTC / 装箱本身清白，钱全花在"从 app0 读 glyf"。**方法论教训**：此前 d118/d119 探针用 `FT_New_Memory_Face` 测 freetype，与被测对象（libvita2d 的**文件** face）输入条件不一致，导致连续三轮把矛头指向 libvita2d 内部缓存。

**根治（d122）**：启动时把字体文件一次性读进 RAM 常驻（UMA 架构，无需搬显存），字体对象改走 `vita2d_load_font_mem(buf, len)`（**只存指针不拷贝，buffer 必须常驻**）。真机 `warm total` **5315ms → 65ms**（81×），`font preload done 22/22` 正常，开机到主界面总开销 ≈665ms（其中读盘 ~435ms 占大头）。

**随后清理（d123）**：预热已无意义，**删掉开屏画面与全部字形预热逻辑**（`pages_warm_all` / `ui_warm_pass` / `settings_scroll_to` / `SPLASH_BG_FILE` 等一并移除），`ui_run` 直接 `font_preload_all()` 建齐字号字体对象（`font_preload_all` 保留：它把字体对象的创建挪到帧外，堵住"渲染中途建 GPU 纹理"的隐患）。代价：读盘那 ~0.43s 无画面（黑屏），观感可接受。

**字体对象与语言地区（d124-d126）**：字体换 Noto Sans（拉丁 + CJK 简/繁/日三份地区版本，见 §5.5）。字号槽 `g_fs[]` 一次建齐 lat+cjk 两份，CJK 槽按**当前界面语言**算（`cjk_slot_current`）、**不能沿用该次调用的 `cjk` 参数**——建槽通常由"要拉丁"(cjk=0) 的那次调用触发，若沿用参数会把 CJK 也建成拉丁字体，表现为**所有汉字渲染成方块**、且 `font preload` 仍报满数（d125 修复）。换语言时在每帧 `start_drawing` **之前帧外**重建 CJK 字体对象（`font_reload_cjk`：释放旧的、按新槽 `load_slot`）——`vita2d_load_font_mem` 会建 512×512 显存纹理，落在渲染 pass 中途有 GPU crash 风险；首次切到某地区读盘 ~1.6s（16MB），之后常驻 RAM——**该 1.6s 已于 d148 在设置页内消除，见下**。

**设置页字体预读（d148）**：语言行只在设置页，故那 1.6s 只会发生在设置页内。现在**进设置页即起低优先级线程后台预读"另外两份 CJK"**（拉丁与当前语言那份本已常驻），页内切语言退化为从 RAM 建字体对象——真机实测相邻两次 `font_reload_cjk` 间隔 **1~3ms**（十次连续切换无卡顿）；**出页停线程并释放非当前语言那份**，页外常驻 ≈17MB 与从前一致，页内峰值 ≈49.9MB（真机三份同驻无 `malloc` 失败）。读盘侧加 `EMPTY/LOADING/READY` 状态机 + **CAS 抢读盘权**（预读线程与"页内切语言"的主线程可能同时要同一份，各读一遍会白占 16MB 且其中一份永远泄漏）、256KB 分块（使线程能在出页时及时收手）、**整份成功才发布**（永不存在半份 buffer）；释放顺序"停线程 → 等退出 → 才 free"，并按 `cjk_slot_current()` 只清非当前语言那份。进出走**显式钩子**——色盘页 / 目录选择页退出会把 `page` 设回 `PAGE_SETTINGS`，按"页边沿"判断会把进子页误判成离开设置页；"接收请求顶掉设置页"这条路径也在 `open_recv_request` 收尾。`font_reload_cjk` 的调用点同时由 `start_drawing` 前挪到 swap + `wait_rendering_done` 之后（换字体等待期间屏上已是新语言界面）。详见 §1「实现现状」。

### 5.8 行几何与长文本口径（d149~d157 定稿）

**只收敛"几何参数入口"，不做样式表覆写层。** 原"样式表"方案（默认一套样式 + 调用点覆写数值 / 字号）能覆盖的只有值行那一族，两行排 / 密集行反正要自绘，多一层"默认表 + 覆写"只会让排查观感问题时多跳一层，故弃用；`RowGeom` 是输出参数，"要偏离就改取回的字段"已经买到了"一处调间距"的收益。

- **几何常量单一来源（`src/ui/ui.h`）**：页头 `HDR_H 52` / 页脚 `FOOTER_H 46`；列表可视区 `LIST_TOP 76` / `LIST_BOTTOM 492` / `LIST_VIEW_H`；行 `ROW_H 56`（可见高）/ `ROW_STRIDE 62`（步进）/ `ROW_PAD_X`、`ROW_PAD_R 24` / `ROW_GAP 12`（主文本与右端元素最小间距）；行内字号档 `SC_TITLE 1.7` / `SC_GROUP 1.05` / `SC_MAIN 1.25` / `SC_SUB 1.0` / `SC_DENSE 1.1`（像素字号 = scale × 20，见 `w_font_px`）。**收敛前同一个概念有 2~5 个取值**：列表顶 76 / 104（主页两栏）/ 68，行步进 62 / 60 / 58，左内边距 20 / 24 / 40 / 48 / 60，右锚点 5 种算法。
- **`row_geom(Rect, RowKind, int reserve_right, RowGeom *g)`（`widgets.c`）**：把行型翻译成 `x_text`（内容左锚点）/ `x_right`（右端元素右边缘）/ `w_text`（主文本可用宽，已扣 `reserve_right`）/ `y_main` / `y_sub` / `main_sc` / `sub_sc` / `row_h`；页面拿结果自己画内容。配套 `w_text_right(x_right, …)` 收掉原先 4~5 种手写右对齐。行型只有 3 档：
  - `ROW_VALUE` —— 单行主文本 + 右端（文字 / 色块 / ✕ / 勾选）：设置页、文件浏览、主页已选文件行、接收设置行；**右端是什么不改变几何**，故行尾控件不是独立行型，走 `reserve_right`。
  - `ROW_2LINE` —— 主上副下：主页设备行、设置页保存目录行。
  - `ROW_DENSE` —— 单行 + 下方附属进度条：进度页。
- **长文本三种截断口径（定死，页面按内容类别选）**：路径 / 目录字符串（保存目录、当前路径、已选文件完整路径）→ `w_text_lead`（**头部省略**，画成 `…/PSPSEND/Download`，末级目录 / 文件名才是要看的那段）；名字类（文件名 / 目录名）→ `w_text_mid`（中间省略，保住扩展名）；其余不受本端控制的文本（对端别名、提示句、平台类型）→ `w_text_clip`（尾部截断）。三者都必须给 `max_w`，**不许用裸 `w_text` 画长文本**（放不下会压到相邻内容上）。
- **不纳入本次收敛**：页头 / 页脚 / 弹窗 / 色盘页各有自己的模块；设置页的分组标题行、logo 行、适配说明行不是"行"，色盘页 HSV 条同理（常量仍在各页内）；主页两栏的 `PANE_*` 仍在 `pages_internal.h`（栏宽 / 栏间距是两栏专有，不参与 `row_geom`）。

## 8. 风险与注意

- multipart 边界解析（上传 body 格式以协议文档为准）
- 大文件流式写盘（内存红线）
- 并发多文件上传（一个 session 多连接）—— **两侧都已落地**：接收侧 d68（按文件独立 busy，逐文件并发收体）、发送侧 d144（N 个 worker 共享取号并发上传，N = config `maxParallel` 上限 6，见 §1「实现现状」）
- 网络异常处理：断连、超时、设备休眠、飞行模式恢复
- 内存监控调试：`mallinfo()`（newlib 堆）+ `sceKernelGetFreeMemorySize()`（系统余量）——注意统一内存下显存块（sceKernelAllocMemBlock）不计入 mallinfo，需结合查看
- 传输速度预期：**下行 5.43~5.54 / 上行 4.72~4.85MiB/s**（d181 裸 TCP 标定，见 §4.5；802.11n 单天线，上下行不对称、socket 缓冲已最优），实测接收 5.21 / 发送 4.66MiB/s，两端均已到顶。早期"10~20MB/s"的乐观估计已被实测推翻
- 发现侧的硬约束（d193）：官方 2.x **register 成功才入库**、总预算 **500ms**；本机单条 TLS 握手 ~240ms，因此**同一时刻只允许一条公告对应的握手在跑**（三份公告错峰 1s/2s）。另：曾用 ping 测得「Wi-Fi 省电模式」把 RTT 从 ~1.9ms 拉到平均 **60ms**（峰值 148ms，锯齿状），一度怀疑它影响发现；但真机端到端实测（省电开 / 关各测）**发现速度与传输吞吐均无明显差异**，故不作为影响因素——802.11 省电只在**空闲期**生效（doze 后按 DTIM/beacon 周期唤醒，beacon 通常 100ms），有持续业务时网卡保持唤醒，故空闲 ping 的 RTT 差异不代表传输期性能。该开关属系统设置，应用层也改不了
